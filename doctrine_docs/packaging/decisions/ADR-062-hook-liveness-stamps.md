# フックは発火の印を残し、対の食い違いから拒否経路の欠落を疑う

## 背景

ガードの故障は証跡を残さない。拒否が一件も起きなかった状態と、拒否できなくなった状態は、外から見て同じ形をしている（ADR-050、NONGOAL 第9項）。配線の欠落で SessionStart だけが動く構成では、注入も監査の要約も健全なまま、拒否だけが消えている。ADR-050 はこの検出を「やらないこと」に置き、機構が入った時点で第9項を狭めると予告した。本決定がその機構の最初の段である。

使える事実が一つある。**ガード（PreToolUse）とリンタ（PostToolUse）は、全ての段階の配線で同じ編集の出来事に対で結ばれ、同じ包みで配られる。** 版が揃うので、「リンタは発火の印を残しているのに、ガードの印が無い・古い」という食い違いは、古い版の名残ではなく配線の欠落を意味する。

## 却下した選択肢

- **機能カナリア（意図的な違反を投じて拒否の往復を確かめる）**: 拒否できることの直接の証跡になるが、違反を作る側の安全装置と偽陽性の設計が要り、版を分ける規模がある（ADR-050 の判断を維持）。印の対はその手前の安い段である。
- **印を `.governance-state` に書く**: あのファイルは手で書く定例の記録で、git の追跡下にある。フックが毎回書けば差分が汚れる。印は実行時の状態であり、追跡しない置き場（`.claude/.cache/`。監査の要約と同じ）に置く。
- **全フックの印を配線表と突き合わせる**: 実効の配線は段階（Level 2/3/4）と利用者の設定で変わり、実行時に確実には読めない。「配線されているはず」の推定と実態の照合は偽陽性の源になる。全段階で不変の対（ガード Pre とリンタ Post）だけに絞る。
- **warn 以上で挙げる**: 印は間接の証跡であり、拒否できないことの直接の証明ではない。advisory に留め、点検（配線の確認）を促すまでとする。

## 決定

1. **三つのフックが発火の印を残す。** 注入（SessionStart）・ガード（PreToolUse のときだけ）・リンタ（PostToolUse）は、起動のたびに `.claude/.cache/hook-stamps` へ「鍵: 時刻」の一行を書く。書き込みは最善努力で、失敗してもフックの本務を妨げない。
2. **読み手と判定は `_auditcache` に一度だけ置く**（ADR-053 と同じ原理）。判定規則: リンタの印があり、かつガードの印が無いか、リンタの印よりガードの印が 60 秒超古いとき、「拒否経路の欠落の疑い」。印が無ければ何も言わない（古い版からの更新直後は印が育つまで沈黙する — 前方寛容）。
3. **鼓動（UserPromptSubmit）が疑いを毎プロンプト告げ、監査が `guard_liveness_gap`（advisory）で挙げる。** どちらも同じ判定関数を呼ぶ。
4. **NONGOAL 第9項を狭める。** 「配線されているのに発火していない」対の食い違いは検出するようになった。依然として保証しないのは、ガードが実際に違反を拒否できること（拒否の往復。機能カナリアの領分）である。

## 帰結

- SessionStart だけが動く欠落構成が、編集が一度でも走れば次のプロンプトの鼓動と次の監査で名指しされる。
- 印の書き込みは一行のファイル更新であり、フックの応答時間に載らない。git の差分も汚さない。
- 検査名が一つ増える（転記表・ICD・SPEC-011 の同時更新を列挙添字の凍結が強制する）。
- 既知の限界: 編集が一度も走らないセッションでは食い違いは生まれない（信号が無いだけで、欠落が無いことの証明ではない）。ガードの印があっても、ガードが正しく拒否するかまでは言えない（機能カナリアは別の版）。Bash だけのセッションはガードの印だけが進むが、対の規則はリンタ側を起点にするので誤検出しない。
