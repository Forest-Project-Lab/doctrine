# 体系は段階と版を自己認知する — 版の切替の検出と Level 昇格の一度きりの案内

## 背景

推進系の網羅の点検で、三つの穴が残っていた。

1. **版の切替を誰も見ない。** Hook の配線はセッション開始時に固定される（DECIDED-001 事実8）。セッションの途中でプラグインの版が上がると、以後のフック起動は新しいコードを実行するのに、セッション冒頭に注入された契約と配線は古い版のままになる。この食い違いを検出して「新しいセッションを開始せよ」と言うものが無かった。
2. **Level 昇格の判断材料を誰も示さない。** 既定の Level 2 には SessionEnd の監査が無く、全件検査は CI が担う。いつ Level 3 に上げるべきかは人の判断だが、判断の機会そのものが提示されない — 利用者が仕組みを知らない前提（導入は一言、以後は促し駆動）と矛盾する。
3. **CI の敷設は検出できない。** 統治はリポジトリの中で閉じ、外部の実行環境（CI が組まれているか・動いているか）を感知する手段を持たない。検出できないものを検出しているように見せない — 境界は正本に書く。

## 却下した選択肢

- **版の照合を監査の検査にする**: 監査は SessionEnd に走る。「再起動せよ」はセッションの中で言わなければ実行可能でない。毎プロンプトの鼓動が言う。
- **全フックの版を突き合わせる**: 同じ包みで配られるので、注入（セッション冒頭の版）と鼓動（今の版）の二点で足りる。点を増やすほど印の書き込みが増えるだけで情報は増えない。
- **Level 昇格を自動で行う／繰り返し促す**: 段階の選択は運用の判断であり自動化しない（docs-system-init と同じ線）。繰り返し促せば雑音になる（RESEARCH-003 類型9）。判断材料を一度だけ示し、記録して黙る。
- **CI の敷設を設定キーで自己申告させる**: 申告と実態の食い違いを検める手段が無い。検証できない申告は誤った安心の素（ADR-050 の判断と同じ）。非目標として明文化する。

## 決定

1. **注入は発火の印に版を刻む。** SessionStart で、実行中のコードが属する包みの版（`plugin.json` の version）を印のファイルへ書く（鍵 `hook_inject_version`）。読めなければ書かない（最善努力）。
2. **鼓動は版の食い違いを毎プロンプト検める。** 今の自分の版とセッション冒頭の版が読めて、かつ異なるとき、「版がセッションの途中で切り替わった。配線と契約は古いままなので、新しいセッションを開始する」と告げる。判定は共有コア（`_auditcache.version_drift`）に一度だけ置く。どちらかが読めなければ黙る（前方寛容 — 古い版からの更新直後を騒がせない）。
3. **Level 昇格の案内は一度だけ出す。** Level 2 の統治木で、全件監査の実績（読める要約）が確認できたとき、鼓動が「Level 3 にすれば SessionEnd の監査と督促が常時になる。上げるなら `_system/.docs-level` に `level: 3`」という中立の案内を一度だけ出し、案内済みの印（鍵 `level_hint_shown`）を残して以後は黙る。昇格するかは人の判断のまま。
4. **CI の敷設は検出しない（NONGOAL 第14項）。** 統治はリポジトリの中で閉じる。感知できるのは CI が残した成果物（要約）までであり、敷設・稼働そのものの証跡ではない。

## 帰結

- 「版を上げたら新しいセッション」という、利用者が覚えるしかなかった運用知識が、覚えなくてよい促しになる。
- Level 2 に留まる体系にも、昇格の判断機会が一度だけ届く。雑音は増えない（一度きり・中立・記録して黙る）。
- 保証の地図がまた一つ閉じる: 推進系の網羅の穴のうち、実装で埋まるものはすべて埋まり、埋まらないもの（CI 検出）は非目標に並んだ。
- 既知の限界: 版の食い違いの検出には、新しい版の鼓動が一度走る必要がある（更新の瞬間そのものは見えない）。同じ版番号のまま中身だけ差し替えた更新は見分けられない。Level の案内は「実績の確認」を要約の存在で近似する — 要約を手動監査で作った場合も案内は出る（それも実績であり、誤りではない）。
