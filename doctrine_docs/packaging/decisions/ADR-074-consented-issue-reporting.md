# 不具合の報告は「検出は機械・送信は人」の二層に分ける

## 背景

フックの入口スクリプトは実行時例外を握りつぶして会話を守る（正しい挙動）が、
握りつぶした事実は stderr にしか残らず、利用者にも保守者にも届かない。
本プラグインはあらゆるリポジトリから使われるため、不具合の報告には統治対象の
機密（リポジトリ名・パス・文書の内容）が混入する危険が常にある。一方、
DECIDED 事実7 は「スクリプトは通信しない」を確定しており、スクリプト自身に
送信させる設計は取れない。[R11]

## 却下した選択肢

- スクリプトが issue API へ自動送信する。事実7（通信しない）に反し、承認の
  ない外部送信は「構造で守り、判断は人に残す」思想とも衝突する。
- 例外の文字列（`str(exc)`）をそのまま記録する。OSError 等の例外文には
  統治対象のパスが混入する。LLM の注意力による黒塗りは保証にならない。
  記録の時点で自由文を捨てる許可制だけが構造的に安全である。
- 報告の手順を8個目の技能にする。DECIDED 事実8（技能は7個に固定）の置換が
  要る。報告の頻度は低い見込みで、恒久の技能一枠に見合うかは実績を見てから
  裁く。まずは鼓動の自己完結文で賄う（移行キャンペーンと同じ型）。

## 決定

不具合の報告を二層に分ける。検出と記録は機械（ローカルのみ）、起草と送信は
LLM と人（承認ゲート必須）。

- エラージャーナル: 入口スクリプト5本（ガード・リンタ・注入・鼓動・監査）の
  例外処理が、`.claude/.cache/doctrine-errors.jsonl`（git の追跡外）へ要約を
  最善努力で追記する。読み書きは共有コア `_auditcache` に一本化し、書式の
  正本は SPEC-021 に置く（発火の印と同じ形）。
- 許可制の記録: 記録するのは 部品名・例外の型・plugin 内の発生位置
  （ファイル名と行）・プラグインの版・時刻 だけ。例外の自由文は写さない。
  統治対象の内容は原理的に入らない。上限20件を保つ。
- 促し: 鼓動が、記録が在るときだけ報告の手順を自己完結文で1セッション1回
  出す — ①事象だけの下書きを作る（許可制の項目のみ）②下書きの全文を利用者に
  見せ、投稿の承認を得る ③承認後に利用者の手元の `gh issue create --repo
  Forest-Project-Lab/doctrine` で投稿する（gh が無ければ本文と URL を案内）
  ④投稿できたら利用者に感謝を伝える。報告は任意で、記録ファイルの削除で
  促しは消える。
- 受け側: doctrine リポジトリに issue の定型フォーム（許可制の項目をそのまま
  フォーム化し、冒頭に感謝を書く）を置く。
- 承認なしの外部送信の経路は作らない（NONGOAL-001 へ登録する）。

## 帰結

- 「沈黙する故障の禁止」（R11）が、握りつぶされた例外まで届く。保守者には
  利用者の承認を経た事象だけが届く。
- スクリプトの通信ゼロ（事実7）と技能7個（事実8）は変わらない。
- 保証限界: ジャーナルは最善努力であり、書けない環境では黙って諦める。
  入口5本の外（review-nudge・capture-nudge・precompact-dump 等）の例外は
  まだ記録されない（後続の配線候補）。下書きの最終的な機密判断は、許可制の
  構造に加えて利用者の確認に委ねる。
