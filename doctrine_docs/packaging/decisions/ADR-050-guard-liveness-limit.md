# ガードが拒否できる状態かは検出しないと明記し、機能カナリアを次の版に分ける

## 背景

統治の生存性（`[R11]`）が見ているのは、前回監査の要約の鮮度と定例の期限である（SPEC-021）。これは「監査が動いた」ことの証跡であって、「ガードが今も拒否できる」ことの証跡ではない。

ガードの故障は証跡を残さない。拒否が一件も起きなかった状態と、拒否できなくなった状態は、外から見て同じ形（何も書き出されない）をしている。フックが全部止まったのであれば、セッション開始の契約が届かないことで気づける。しかし配線の欠落で SessionStart だけが動く構成（手動配線のパスの問題、#75）では、注入は届き、監査の要約も新しく、それでいて PreToolUse の拒否だけが消えている状態がありうる。統治は健全に見え、予防の層だけが働かなくなる。

保証限界（`[R9]`）は、何を予防し、何を検出し、何を人間に委ねるかを書けと定める。ガード経路の死活は、現状どの成果物にも書かれていない。穴が開いたまま黙っていること自体が `[R9]` に反する。

## 却下した選択肢

- **いま機能カナリア（意図的な違反を投じて、拒否が起きるかを確かめる仕掛け）を実装する**: ガードの往復（拒否 → 所見 → 監査 → 次の注入）を確かめる仕組みは、それ自体が正しい。しかし違反を作る経路を CI に常設することになり、誤報の手当てと、確かめる側が本物の統治木を汚さない隔離が要る。版を分けるだけの規模がある。穴の明記より先に置くと、明記のないまま実装が長引く。
- **`[R11]` の文言を広げ、ガードの死活も見ていることにする**: 見ていないものを見ていると書くのは、保証限界の偽装である。誤った安心は、限界の明示より害が大きい。

## 決定

二つに分ける。

1. **この版**: 「ガードが起動して拒否できる状態かどうかは検出しない」を、NONGOAL の第9項として明記する。`[R11]` の生存信号が保証するのは、監査の要約の鮮度と定例の期限までであることを、やらないことの側から確定させる。逃げ道は既存と同じで、ガードを逃れた違反は全件監査が後から拾う（NONGOAL 第3項・第4項と同じ構造）。
2. **次の版**: 機能カナリアを別の変更として起こす。入った時点で本 ADR を置換し、NONGOAL 第9項を、そのとき残る限界まで狭める。

## 帰結

- 保証限界の穴が塞がる。「ガードが在ること」を「ガードが効いていること」と読み違えずに済む。
- カナリアを入れる条件と、入れたときに何を書き換えるかが明文になる。第9項は削るのではなく、残る限界まで縮める。
- 既知の限界: 明記は検出を増やさない。この版の後も、拒否だけが消えた構成は、全件監査が後から違反を拾うまで見えない。
