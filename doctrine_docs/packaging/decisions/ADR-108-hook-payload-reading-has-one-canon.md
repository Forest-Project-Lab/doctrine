# Hook の封筒の読み取りを正本に一本化する。上限は正本が持つ

## 背景

Hook が受け取る封筒（標準入力の JSON）を読む実装が、**四箇所に在った。**
正本は共有コアの `read_payload` で、**読む量に上限を持つ**（8 MB で切る）。

| 在処 | 上限 |
|---|---|
| 共有コア `_hookio.read_payload` | **在る**（8 MB） |
| `inject-contract` | 正本を呼ぶ |
| `capture-nudge` | **無し**（`sys.stdin.read()`） |
| `gov-heartbeat` | **無し** |
| `review-nudge` | **無し** |

**三本とも共有コアを既に取り込んでいる。** それでいて封筒の読み取りだけを自前で持ち、
上限を落としていた。

実測した。9 MB の封筒を三本に渡した。

```text
gov-heartbeat  exit=0  出力=718字   （全部読んだ）
review-nudge   exit=0  出力=0字     （全部読んだ）
capture-nudge  exit=0  出力=0字     （全部読んだ）
```

**上限は正本の判断として在るのに、三本はそれを受け取っていない。** これは
日付の解釈（ADR-099）・スカラへの正規化（ADR-101）・設定の読み取り（ADR-104）・
読み取りの門（ADR-107）に続く、**同じ写しの類型の五件目**である。そして四件目と
同じ形をしている —— **正本が持つ守りを、写しが落としていた。**

## 却下した選択肢

**三本に上限だけを書き足す。** 上限の数を呼び手が覚えることになる。**忘れれば無制限**
—— いま起きているのがまさにそれである。しかも数が四箇所になり、変えるときに揃わない。

**上限を外す（緩い側へ揃える）。** 上限は正本の判断である。**緩い側へ揃えない**
（ADR-104 で同じ判断をした）。

**そのままにして註記する。** 註記は読み取りを止めない。

## 決定

**封筒の読み取りを共有コアに一本化する。上限は正本が持ち、呼び手は数を書かない。**

1. **三本の写しを消し、正本を呼ぶ。** 薄い前面も置かない（ADR-099・ADR-101・ADR-104・
   ADR-107 と同じ理由）。
2. **上限は正本が持つ。** 呼び手は上限の数を書かない。
3. **機械が写しを咎める。** 封筒を自前で読む関数が現れたら、メタの受入が落ちる。

## 帰結

- 封筒の読み取りが一本になり、上限が全部の Hook に掛かる。
- **上限を超える封筒は、三本でも空として扱われるようになる**（いまは全部読んでいる）。
  三本とも解析に失敗したときは空を返す設計なので、**degrade の道は既に在る** ——
  封筒が無いときと同じ振る舞いになる（助言を出さずに静かに通す）。
- 保証限界: **上限の 8 MB は見立てである。** 測って出した数ではない（正本の既定を
  そのまま使う）。
- 保証限界: **切り詰められたことは呼び手に伝わらない。** 正本は空を返すだけで、
  「封筒が無い」と「封筒が大きすぎた」を区別しない。**これは既存の挙動であり、
  ここでは変えない** —— 黙って切り詰めない規律（ADR-058）と当たる面なので、別に扱う。
- 保証限界: 機械が咎めるのは名前の形である。別の名前で同じことをすれば掴めない。
