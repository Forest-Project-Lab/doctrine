# SessionEnd は監査を予約する（口には負債だけを置く）

本文で使う語を先に置く。Hook（特定の出来事で起動する処理）の「口」とは、ホストが
その出来事で起動して**完了を待つ**コマンドのことである。ホストがその完了を待つ時間には上限が在り、本文ではこれを「待ちの上限」と呼ぶ。

## 背景

SessionEnd の口には、統治木の全件監査（`docs-audit.py`）を直に置いていた。ADR-119 が
「走った証跡」を、ADR-043 が「次セッションへ要約を渡す」ことを定め、どちらもこの配線を
前提にしている。

2026-08-09 の独立再監査が、この配線が**一度も成立していなかった**ことを実測した。

使い捨ての worktree と隔離した設定ディレクトリで、SessionEnd の口に置いた仕事の所要を
変えながら完了を数えた（各 3 回）。

| 口に置いた仕事の所要 | 完了 | 打ち切り |
|---|---|---|
| 0 秒 | 3/3 | 0/3 |
| 1 秒 | 3/3 | 0/3 |
| 2 秒 | 0/3 | 3/3 |
| 3 秒 | 0/3 | 3/3 |
| 9 秒 | 0/3 | 3/3 |

待ちの上限は 1 秒超〜2 秒未満だった。一方、全件監査の所要は 8.46 / 8.21 / 9.52 秒である。
**口に置いた仕事は、待ちの上限の 4〜9 倍かかっていた。**

帰結は実環境に出ていた。`.claude/.cache/last-audit.json` は `generated_at`
2026-08-04T00:00:00Z のまま 5 日間動かず、そのあいだに統治文書を編集したセッションが
7 件終了して、監査の配送は 0 件だった。打ち切りの事実は標準エラーへ
`SessionEnd hook [...] failed: Hook cancelled` と出ていたが、それを読んで台帳へ積む段は
どこにも無かった。

そして SessionStart は、5 日前の `error 0 / warn 0 / advisory 0` を「前回監査」として
**正の安心のまま注入し続けていた**。暦による古び警告の閾値は 7 日で、5 日はそこに届かない。
実際にはその時点で warn が 4 件立っていた。

これは ASM-001（「SessionEnd は必ず発火する」）の `if_false` に書いたとおりの形である
—— 「外から見た形は『走ったが変化が無かった』と区別できず、古い健全信号が正の安心として
注入され続ける」。想定は登録されていたが、破れていることを機械は言わなかった。

## 却下した選択肢

- **監査を速くする。** 274 文書で 8 秒である。待ちの上限が 2 秒未満である以上、定数倍の改善では
  届かない。しかも木が育てば所要は伸び、待ちの上限は伸びない。同じ壁に必ず戻る。
- **口に `timeout` を足して部分監査にする。** 部分の所見を全件の要約として書くことになり、
  「判定を書けないときは沈黙して開かない」（DECIDED-001 第12項）に真っ向から反する。
- **打ち切りを検出して警告するだけにする。** 症状を告げるが監査は依然として走らない。
  R11 が求めるのは生存であって、死亡の通知ではない。
- **鼓動（UserPromptSubmit）で監査を走らせる。** per-turn の持ち時間（WATCH-001 第8項。
  guard+linter の対で 1.0 秒未満）を 8 秒の仕事が食い潰す。毎ターン買う仕事ではない。
- **負債を置かず、切り離した子だけに頼る。** 切り離しが効かない環境（子を起こせない・
  ホストがプロセス群ごと畳む）で、走らなかったことが痕跡なく消える。いま直そうとしている
  形そのものへ戻る。

## 決定

1. SessionEnd の口は**監査しない。予約する**。配線は `--detach` を付ける。
2. 口がすることは二つだけとする。**負債の印を置く**こと（`.claude/.cache/audit-due/<識別子>.json`）
   と、監査を**切り離した子**（`start_new_session=True`）へ渡すことである。口は即座に 0 を返す。
3. 負債の印は、**要約を書けたときだけ**消す（子が `--clear-due` を持つ）。走っただけで消すと、
   書けなかった実行が負債を帳消しにし、次のセッションは古い要約を「済んだもの」として受け取る。
4. SessionStart の契約注入は、未消化の負債が在れば**要約より先に**それを告げる。暦の閾値
   （既定 7 日）を待たない。負債はファイルの実在であって、日数の推定ではない。
5. 切り離しに失敗したときは、負債の印を残したうえで一行告げる。**沈黙して開かない**
   （DECIDED-001 第12項）。口は決して 0 以外を返さない —— SessionEnd の口を壊すことは、
   監査が遅れることより悪い。
6. Level 2 では負債の概念を持たない。SessionEnd の監査がそもそも無い（ADR-019）ので、
   負債を言うのは誤報になる。

## 帰結

- 監査は実際に走るようになる。実測（使い捨て環境・修正後）: 打ち切り 0 件、SessionEnd 直後に
  `audit-due/<セッション id>.json` が在り、15 秒後には `last-audit.json` が書かれて負債の印が
  消えている。
- 走らなかったときは、**次のセッションの冒頭に負債として出る**。要約の古さではなく、
  終了の回数で数える。一件目から出る。
- ADR-119 の印（`hook_session_end_audit` / `hook_session_end_write`）は変えない。印は
  「走ったか・書けたか」を、負債は「予約したのに済んでいないか」を言う。役割が違う。
- 待ちの上限の値はホスト依存であり、ここで測ったのは Claude Code 2.1.223 を devcontainer で
  動かした一例である。決定が依存するのは「待ちの上限が有限で、全件監査より短い」ことだけで、
  具体的な値には依存しない。
