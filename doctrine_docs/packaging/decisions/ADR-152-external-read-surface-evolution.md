# 外部読み口の進化規約 — 鍵の追加は互換、壊す変更は版上げ、診断は標準エラー

## 背景

issue #294 は宣言済みの読み口へ欄を足す提案を「既存の消費者は無視できる（後方互換）」と
述べたが、その互換に契約上の根拠が無い（権限は ADR-151）。「前方寛容」の語は状態ファイル
（ADR-042）や実装の内部（IMPL-021）に散在するだけで、外部の JSON 読み口には掛かって
いない。ICD-002 の「ちょうど五項」のような固定の書き方だけでは、最上位の鍵を足す変更が
互換かどうかを読み手が判じられない。読み口は今後も増える（監査要約は ADR-137、追跡索引は
ADR-112 が一口ずつ宣言してきた）ので、口ごとに規約を発明しないよう一度で決める。

## 却下した選択肢

- **中央に「外部読み口の一覧」を作る。** 二箇所に列挙を持つとドリフトする。ADR-137 が
  同じ理由で ICD 間の相互参照を却下済み。規則だけを横断で決め、列挙は各ドメインの ICD に残す。
- **欄を足すたびにスキーマ名の版を上げる。** 消費者は版名の照合で毎回壊れる。追加が
  互換である規約が無いことが問題なのであって、版上げの乱発は解にならない。
- **何も決めない。** 欄の追加のたびに互換性の議論が再演され、#294 のような外部からの
  提案を受ける床が無いままになる。

## 決定

外部読み口（体系の外の消費者へ宣言した CLI の返す値）の進化規約を、横断の確定事実として置く。

1. 体系の外の消費者が依存してよいのは、各ドメインの ICD の外部条項が宣言した CLI の
   返す値だけとする（宣言なき消費は、実装の内部形が黙った契約になる）。
2. 宣言済みの JSON では、既知の最上位の鍵の意味を変えずに鍵を**足す**変更は互換とする。
   読み手は未知の最上位の鍵を読み捨ててよい。
3. 既知の鍵の意味・形を変える、または鍵を消す変更は互換を壊す変更であり、スキーマ名の
   版を上げる（例: `trace-index/1` → `trace-index/2`）。
4. 機械向けの JSON は stdout へ、診断は標準エラー（stderr）へ出す。stdout を診断で汚さない。

この規約を DECIDED-001 の事実13 として追加し、外部条項を持つ ICD（graph・audit・authoring）が
一行で採用する。「ちょうど五項」のような**項目の中の**固定は従来どおり効く —— 固定と
互換の境目は「最上位の鍵の追加」だけに引く。

## 帰結

- #294 の提案（返り値へ欄を足す）は、この規約の上で互換の変更として受けられる（ADR-155・ADR-156）。
- 外部条項を持たないドメイン（model・guard・lint・context）には適用の実体が無く、採用の行も足さない。
  外部の口を新設するときに、その ICD が本規約を引く。
- 保証限界: 規約は読み手の側の読み捨てを強制できない。未知の鍵で壊れる消費者は、自身の
  読みを規約に合わせる（doctrine 側は鍵の追加を互換と扱ってよい根拠を得る）。
