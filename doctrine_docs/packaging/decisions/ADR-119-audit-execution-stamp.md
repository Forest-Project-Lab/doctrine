# 監査は走ったこと自体の印を残し、鮮度の警告が不実行と書き込み失敗を区別する

## 背景

全件監査の要約は、体系の適合状態についての唯一の全体像である。鮮度の警告（R11）は
その古びを毎ターン告げるし、実際に働いた —— 2026-07-28 から更新が止まったことは
警告として出た。しかし警告が言えるのは症状だけで、原因が「監査が走らなかった」のか
「走ったが要約を書けなかった」のかを区別できない。区別できないまま 8 日が過ぎ、
版の遅れという別の疑いへ時間が費やされた（後に反証された。三世代前の配布物も
同じ配線を持っていた）。

書き込みの失敗は現に沈黙する。置き場が書けない状態で走らせると、標準エラーへ一行
出るだけで終了コードは 0 のままである（実測）。要約は前の内容のまま残るので、
外から見た形は「走らなかった」ときと同じになる。

## 却下した選択肢

- **印の不在から不実行を断ずる**: 段階と利用者の設定によって SessionEnd の監査を
  持たない構成があり、不在を根拠にすると誤報になる。ADR-062 が同じ理由で
  「配線表との突き合わせ」を却下している。
- **要約の書き込み失敗を終了コードへ出す**: 現行仕様は「失敗しても 0 を保つ」と
  明示して決めている。覆すなら別の決定が要り、SessionEnd の後始末を壊す危険も
  ある。ここでは触らない（可否は所有者判断として台帳に残す）。
- **監査の検査（findings）として挙げる**: 監査が走っている最中は印が必ず新しく、
  自分について何も言えない。読み手は次のセッションの鼓動でなければ意味を持たない。

## 決定

要約の書き出しを指示されたとき（`--summary-out`）、監査は走ったこと自体の印
`hook_session_end_audit` と、書けたかどうかの印 `hook_session_end_write`
（`ok` / `failed`）を残す。鼓動は、鮮度の警告を出すときに**走った証跡が在れば
原因の側を名指しする**。証跡が無ければ従来どおり症状だけを告げる。

## 帰結

- 判定は `_auditcache.audit_write_gap` に一度だけ置く（ADR-062・ADR-053 と同じ
  原理。読み手ごとに答えを割らない）。規則は、印が在り、かつ書き込みの印が失敗を
  告げるか、印が要約の日付より新しいとき「走ったが書けていない」。
- 印が無いときは何も言わない（前方寛容）。古い版からの更新直後や、監査を持たない
  段階では印が育たない。**不在は不実行の証明ではない。**
- 印の書き込みは最善努力で、失敗しても監査の本務を妨げない（ADR-062 と同じ）。
  置き場は `.claude/.cache`（実行時の状態は配布物の下へ書かない。WATCH-001 第9項）。
- 依然として区別できないのは「SessionEnd がそもそも発火しない」場合である。
  印も要約も動かず、外からは静かなままになる。これは残す限界として台帳に持つ。
