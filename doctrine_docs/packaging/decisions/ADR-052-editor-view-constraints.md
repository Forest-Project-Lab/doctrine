# 編集画面の表示層は統治判断を持たず、索引が無ければ黙る

## 背景

編集画面の拡張（コードに手を置いたとき、その行の根拠・決定・試験・最終確認を示す表示）の構想がある。目的は到達しやすさである。統治が構造として持っている事実を、文書を読みに行かなくても人が受け取れるようにする、副産物としての表示層である。

実装はまだ遠い。前提となるコード注釈の書式（ADR-048 第4項）が無く、注釈が無ければ表示する錨も無い。錨の無い表示が出せるのは「語の近い文書」だけであり、それは位置付けの不明な関連を編集画面へ配って回る装置になる。体系が最も避けようとしている状態を、体系自身が広い面へ運ぶことになる。

仕様はまだ書けない（表示するものが無い）。しかし制約はいま書ける。後から足すと、拡張のために中核を曲げる圧力が生じ、曲がった後では戻せない。

## 却下した選択肢

- **拡張の仕様ごといま書く**: 注釈の書式が無い段階の表示仕様は、当て推量になる。抽象の先取り（`[R8]`）であり、書いたものが後で全て変わる。
- **構想ごと退ける**: 到達しやすさの目的は正当である。構造として管理された事実を人が受け取れないのは、統治の価値を一つ落としている。退けるのではなく、順序と境界を先に決める。
- **何も決めずに寝かせる**: 制約の無い構想は、実装が始まった時点で最も安い形（中核へ手を入れる形）に落ちる。安いのは書いた後ではなく、書く前だけである。

## 決定

編集画面の表示層を作るときの制約を、実装より先に三つ凍らせる。

1. **表示層に限る**: 統治判断を持たない。拒否も差し止めもしない。判断は中核とフックが持ち、表示層は結果を読むだけである。
2. **索引が無ければ何も示さない**: 推し量りで埋めない。錨（コード注釈から導いた索引）が無ければ黙って劣化する。「語が近い文書」を関連として示すことは、しない。
3. **中核は CLI が持つ**: 表示層に統治の処理を置かない。読むのは決定論で描かれた値だけとする。編集画面の側の作法（`API`）に依存する処理を中核へ持ち込まない。

実装の順序も動かさない。注釈の書式（`SPEC`）→ 索引の投影 → 表示層。前の段が無いまま次へ進まない。

## 帰結

- 表示層のために中核を曲げる圧力が、構造的に起きなくなる。表示層が壊れても中核の答えは変わらない。
- 「関連しそうな文書」を出す装置に堕ちる道が塞がる。示せるものが無いときは黙るのが正しい挙動だと、先に決まっている。
- 既知の限界: 本 ADR は制約だけであり、拡張の仕様ではない。何を示すか、どう示すかは、注釈の書式が定まってから別の `SPEC` で決める。表示層が支援技術にとって読みやすいかは、この制約とは別に測る必要がある（平文と Markdown より読みにくい形にしては、到達しやすさの目的を裏切る）。
