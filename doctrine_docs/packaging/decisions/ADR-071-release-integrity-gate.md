# リリースの整合を CI の門で検める — 変更履歴の書き忘れの構造的な防止

## 背景

版番号の正本（`plugin/.claude-plugin/plugin.json`）と marketplace.json の一致は
単体テストが強制する（TEST-020）が、CHANGELOG（リリースごとの変更を利用者向けに
記す変更履歴ファイル。実体は CHANGELOG.md）はどの門も見ていない。「版は上がった
のに変更履歴が無い」「変更は入ったのに記録が無い」状態が main に入れた。

書き忘れの根は運用の形にある。リリース時に、それまでの変更をまとめて思い出して
書く運用は、思い出せなかった変更を無音で落とす。変更のたびに一行を積む場が無く、
積み忘れを指す照合も無かった。

## 却下した選択肢

- **コミットの題名から変更履歴を自動生成する**（semantic-release 等）:
  この CHANGELOG は「なぜ・何が変わったか」を利用者向けに書いた散文であり、
  コミットの題名の羅列に置き換えると読み手への価値が落ちる。第三者依存も
  持ち込む（ADR-031 に反する）。機械に書かせるのではなく、人が書いたかを
  機械が検める。
- **監査の検査にする**: 監査は SessionEnd に走り、pull request の差分という
  単位を持たない。「この pull request が記録を積んだか」は合流の門でしか
  判じられない。CI が層である（フックを通らない経路を CI が補う形は
  スキーマの門と同じ。NONGOAL 第4項の補いの線）。
- **ガード（Hook）にする**: ガードは一回の編集を見る。記録の義務は編集単位
  ではなく変更のまとまり（pull request）単位の性質であり、編集のたびに
  CHANGELOG を要求すると誤検出だらけになる。
- **plugin.json と marketplace.json の一致も新しい検査に含める**: TEST-020 が
  既に強制している。同じ規則を二か所に書くと食い違いの種になる（DECIDED-001
  事実1と同じ原理）。新しい検査は CHANGELOG との整合だけを受け持つ。
- **免除の仕組みを作らない**: 記録に値しない変更（誤字・CI 設定だけの調整）
  まで一行を強いると、門を嫌って迂回する動機を生む（ADR-051 が変更フローで
  同じ判断をした）。無音の迂回ではなく、pull request の題名に印を書く明示の
  免除を用意する。

## 決定

1. **リポジトリ直下 `scripts/release-check.py` が検める。** 自己適用の一本で
   あり（SPEC-023 と同じ置き方）、配布物に含めない。標準ライブラリのみ。
   CI（checks.yml）が毎回走らせ、違反は error で門を閉じる。
2. **版の整合**: CHANGELOG の先頭の版付き節（`## [X.Y.Z] — 日付` の形）が、
   版番号の正本（plugin.json の version）と一致し、日付を持つこと。
3. **記録の義務**: pull request の差分が `plugin/` に触れるなら、同じ差分が
   CHANGELOG.md にも触れること。常設の「未リリース」節に一行を積むのが正規の
   道で、リリース時にその節へ版番号と日付を付ける。
4. **明示の免除**: pull request の題名に `[no-changelog]` を含めれば記録の
   義務だけを免れる（版の整合は免れない）。免除は差分に残らないので、迂回は
   題名という読める場所に証跡を残す。

## 帰結

- 「リリース時に思い出して書く」が「変更のたびに一行積む」に変わり、
  書き忘れは合流の門で止まる。リリース手順は PROC-001 に正本化する。
- 仕様は SPEC-027、受入は TEST-027 が凍結する。
- 既知の限界: 積んだ一行の中身の質までは検めない（意味の判断は査読に残る。
  NONGOAL 第1項と同じ形）。main へ直接 push する経路は pull request の差分を
  持たないため、記録の義務は検めず版の整合だけを検める。
