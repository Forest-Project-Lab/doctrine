# コードシンボル追跡のための外部依存の評価（保守性・セキュリティ・被覆・移行）

## この調査の位置づけ

段1（統治範囲をコードシンボルへ広げる）を決めるにあたり、DECIDED-001 事実7（すべてのスクリプトは標準ライブラリだけで動く。pipにも通信にも依存しない）を置換してよいかを判じるための材料である。**結論を出すための手続きではない。** 置換に値しないという結論もありうる前提で調べた。

本文書は調査であって決定ではない（`llm_context: never`。決定は ADR へ、確定事実は DECIDED へ）。

## 1. まず要求を分解する（依存が本当に要るのはどこか）

「コードシンボルまで追跡する」を、実際に要る機能へ割る。

| 要求 | 内容 | パーサが要るか |
|---|---|---|
| R-a | 注釈が指す id が実在するか | **不要**（注釈を grep し、dep-graph に問う） |
| R-b | 注釈が廃止・置換済みの id を指していないか | **不要**（同上） |
| R-c | 現行 SPEC に対応する注釈が一つも無い（下向き孤児） | **不要**（同上） |
| R-d | 注釈を付けた後にコードが変わった（古び） | **範囲の確定が要る**。ここだけがパーサの出番 |
| R-e | 関数が改名・移動しても追い続ける | **パーサでは解けない**（後述） |

四つのうち三つは標準ライブラリで閉じる。依存が効くのは R-d だけである。

### R-e について（重要）

tree-sitter は**単一ファイルの一時点を構文木にする道具**であり、版をまたいだシンボルの同一性という概念を持たない。改名の追跡は git の履歴と発見的手法の領域で、tree-sitter の守備範囲の外である。したがって、**最も重い依存を入れても、最も難しい要求は解けない**。ここを取り違えると、払う対価と得るものが釣り合わない。

## 2. 候補と評価

### 2.1 tree-sitter（py-tree-sitter + 文法パッケージ群）

**保守性**

- 破壊的変更の履歴が濃い。0.22.0 で `Language(path, name)`・`Language.build_library(...)`・`Language.name` を削除し、`Language()` は整数引数一つだけを受ける形へ変わった。`Query.captures/matches` の引数もキーワード必須になった。0.24 で Python 3.9 を切った。現行は 0.26.0（2026-06-30 公開、Python >= 3.10）。
- **ABI のずれが構造的に続く。** 文法は本体と別々に版が進み、生成に使った ABI（13/14/15）が読み手の対応範囲外だと読み込みに失敗する。Emacs・Doom・Zed・NixOS で同じ形の破損が繰り返し報告されている。これは一度きりの不具合ではなく、この生態系の定常状態である。
- **集約層が一度死んでいる。** 多言語を現実的にするための `tree-sitter-languages`（py-tree-sitter-languages）は保守停止し、`tree-sitter-language-pack` が後継となった。派生も複数ある。doctrine が依存するのは本体だけでなくこの集約層であり、そこの担い手が入れ替わる前例が既にある。

**セキュリティ**

- 本体は C の実装で、文法も C へ生成される。**ネイティブコードを、編集のたびに走るフックの中で、信頼できない入力に当てることになる。** doctrine 自身が NONGOAL 第8項で「文書内容は、他者の変更取り込み依頼・外部から取り込んだ依存・展開物としてリポジトリに入りうるため、チーム作成という信頼前提は置けない」と認めている。コードにも同じことが言える。
- CVE-2026-25727（スタック枯渇による停止）が登録されている。深く入れ子にした入力でパーサを落とせる。doctrine の PreToolUse は fail-closed なので、**細工した一ファイルで編集そのものを止められる**（開発者自身の道具に対する可用性攻撃）。fail-open にすれば、今度は予防が黙って消える（ADR-050 で明記したばかりの穴）。どちらへ倒しても代償がある。
- 供給網の面は 305 個以上の文法パッケージが対象になる。ライセンスは許諾的なものに限られている（GPL 系は採らない方針）が、点検すべき出所の数はそれだけ増える。

**配布（ここが決定的）**

- **Claude Code のプラグインには、依存を導入する仕組みが無い。** `plugin/.claude-plugin/plugin.json` が持つのは name・version・description・author・license だけである。フックは `"${CLAUDE_PLUGIN_ROOT}/scripts/*.py"` を直に起動し、解釈系は shebang の `/usr/bin/env python3` が決める。
- したがって外部依存を入れると、利用者は**フックが解決するのと同じ解釈系**へ手で導入せねばならない。それがどれかを、プラグイン側は知ることも指定することもできない（システムの python・pyenv の shim・仮想環境・コンテナのいずれにもなりうる）。
- 導入に失敗したときの壊れ方は二つしかない。ImportError で PreToolUse が落ちて**全編集が拒否される**か、握りつぶして**予防が黙って消える**か。前者は導入初日に使えず、後者は R11 が禁じる沈黙する故障そのものである。
- 車輪は広く用意されている（Windows x86-64/ARM64、macOS x86-64/ARM64、Linux manylinux x86-64/ARM64、musllinux x86-64、RISC-V 64）。**車輪の有無は問題ではない。導入する経路が無いことが問題である。**

**被覆（「あらゆるものを管理できるか」への答え）**

言い切れない。理由は三つある。

1. 305 言語は「すべて」ではない。設定記述・独自言語・DSL・テンプレートは外れうる。
2. 文法ごとに品質が違う。近縁の道具では、ある言語で関係の約6割が取れないという報告がある。**対応言語として並べておいて、実際には黙って落ちる**のが最も危うい。
3. 生成コード・マクロ・条件つき取り込みは、構文木からは意図が読めない。

### 2.2 標準ライブラリの `ast`（Python のみ）— 退けた

依存は無く（解釈系に同梱）、`ast.parse` は評価しないので攻撃面も増えない。doctrine 自身の実装は全て Python なので、自己適用の範囲は覆える。

**それでも採らない。** 言語ごとに範囲の決め方を変えると、「範囲はどこか」という一つの問いに二つの実装が答えることになる。これは重複 id の採用規則（ADR-049）と監査要約の読み取り（ADR-053）で二度直した欠陥類型そのもので、設計の時点で作り込むことになる。加えて、Python だけ精度が高いという状態は保証限界を言語ごとに割り、「対応言語として並べておいて実際の挙動が違う」という §2.1 で退けたのと同じ形になる。

一様に一つの機構で捌くほうが、機構が二つあって片方が優れているより強い。

### 2.3 注釈で範囲を明示する（パーサ無し）

開始と終了を注釈で挟み、その間の内容を hash する。

**保守性**: 依存ゼロ。言語非依存（行注釈さえ書ければよい）。
**セキュリティ**: 読むのは自分の書式だけ。ネイティブコードを持ち込まない。
**被覆**: 行注釈を書ける全ての言語。品質の差が出ない。
**弱点**: 印を二つ書く手間。そして**利用者が終了印を消し忘れる／付け忘れる**という、まさに懸念された故障が起きうる。ただしこれは機械で検出できる（対になっていない印を監査が error で挙げる）。パーサ方式の故障（ABI のずれ・言語ごとの黙った脱落）は、同じようには検出できない。

### 2.4 universal-ctags / 言語サーバ

外部の実行ファイルへの依存で、pip 依存と同じ配布の問題を抱える。言語サーバはさらに起動と常駐が要り、フックの応答時間に載らない。**配布の問題が解けない以上、tree-sitter と同じ壁に当たる。**

## 3. 懸念された三つの故障への当てはめ

| 懸念 | パーサ方式 | 注釈方式（2.3。全言語で一様） |
|---|---|---|
| 忘れる（付け忘れ・劣化に気づかない） | 注釈は一つで済み、範囲は自動。ただし**依存が入っていない環境で黙って劣化**する経路が増える | 印が二つ要る。ただし**対の欠落は機械が error で挙げられる** |
| 消し忘れる（残骸） | コードを消せば構文木からも消える | **終了印だけが残る**ことがある。対の検査で拾う |
| 追従しない（改名・移動） | **解けない**（tree-sitter の守備範囲外） | 解けない（同じ）。hash が変わるので「再確認せよ」までは出せる |

改名の追従は**どちらの方式でも解けない**。ここは保証限界として明記する対象であり、依存の有無で変わらない。

## 4. 移行と退路

外部依存を採った場合に要るもの。

- 導入手順（利用者ごとの解釈系の特定を含む）と、それが失敗したときの挙動の定義。
- 本体と文法の版の固定と、ABI のずれを検出する起動時の点検。
- 依存が無い環境での縮退の定義（黙って縮退しないこと）。
- 閉域・遮断環境での導入経路。
- 退路: 依存を外すときに、索引の書式が依存に縛られていないこと。

注釈方式を採った場合、上の五つは**いずれも要らない**。

## 5. 所見

依存が買えるのは R-d（古びの検出における範囲の正確さ）だけであり、最も難しい R-e は買えない。対価は、配布の経路が無いこと・ABI のずれが続くこと・編集ごとのフックにネイティブコードが入ること・集約層の担い手が替わりうること・言語ごとの被覆を言い切れないことである。

**釣り合っていない。** とりわけ「Claude Code のプラグインに依存を導入する仕組みが無い」は、運用の工夫で埋められる種類の問題ではない。

採るべき形は、2.3（注釈で範囲を明示）**だけ**である。言語ごとの手段を持たず、一つの機構で全言語を同じ規則で捌く。事実7 を触らずに R-a〜R-d を満たし、R-e は保証限界として明記する。

一様であることは、ここでは妥協ではなく利点である。「対応言語」の表を持たないので、表に載っているのに実際は落ちる言語が生まれない。保証限界が一つで済むので、利用者が言語ごとの差を覚えずに済む。範囲を決める実装が一つなので、二つの実装が食い違う欠陥類型（ADR-049・ADR-053）が構造的に起きない。

この所見を採るなら、対応する決定は ADR で起こす。採らない（それでも依存を入れる）なら、§4 の五項目を先に設計してから事実7 を置換する。
