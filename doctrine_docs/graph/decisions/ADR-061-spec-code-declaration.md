# 仕様はコードとの関係を宣言できる — 明示の「対応なし」と、宣言と実態の矛盾の検査

## 背景

追跡から外れる正規の方法が「`## 実装の指紋` の節を消す」しか無かった。節の削除は無音であり、コード側に注釈の対が残っても誰も見ていない（欠陥D）。実際に自分の統治木で、監査の検査一覧（`AUDIT_CHECKS`）を囲む注釈が SPEC-011 を指しているのに、SPEC-011 は節を持たず、この紐は誰の視界にも無かった。

先行事例の教訓（RESEARCH-003 類型11）は「逃げ道のある印は必ず逃げ道として使われる」である。逃げ道を塞ぐのではなく（塞げない — 節の削除は検出できない。git を持たない体系に「前は節があった」という記憶は無い）、**正規の出口を用意して、出口を通った宣言と実態の矛盾を機械で検べる**。

もう一つ、「仕様を書いて実装したのに注釈を入れ忘れた」は、コード側からは原理的に判じられない（ADR-054）。判じられるのは文書側である — 現行の仕様がコードとの関係を何も宣言していない、という状態は数えられる。空欄のセルを構造的に無くす（SPEC-025）の仕様版だが、全仕様へ宣言を一斉に義務づけると、版を上げた利用者の緑の監査に警告が降る。段階を分ける。

## 却下した選択肢

- **全ての現行仕様に宣言を義務づけ、無宣言を warn にする**: 成熟したリポジトリでは版上げの日に数十件の warn が降る。導入初日に警告を浴びせない原則（ADR-056）に反する。無宣言は勘定（件数）と advisory までにし、義務化は使用実績を見て別の ADR で裁く。
- **opt-out をフロントマターのキーで持つ**: 必須キーの集合は確定事実（DECIDED-001 事実3）で凍っており、任意キーを足すと schema の面が広がる。宣言は指紋と同じ節に置く — コードとの関係の記述が一箇所に集まる。
- **節の削除をガードで拒む**: 編集前後の意味の判断が要り、正当な削除（追跡をやめる意思）と事故の削除を機械で分けられない。拒否より宣言の正規化と事後の検算を採る。
- **何もしない（欠陥Dを既知の限界のまま残す）**: 自分の統治木に実例が既にある。注釈の対は書いたのに文書側が沈黙している紐は、指紋の照合が永遠に始まらない。

## 決定

1. **`## 実装の指紋` の節に、指紋の代わりに `- コード対応なし: <理由>` の一行を書けるものとする。** これが「この仕様は意図してコードと結ばない」の明示宣言である。宣言した仕様は下向きの照合（指紋・範囲の有無）の対象にしない。
2. **宣言と実態の矛盾を warn で挙げる（`trace_unexpected_impl`）。** 「対応なし」と宣言した仕様を指す範囲がコードにあれば、宣言が古いか注釈が誤りである。この検査は宣言した文書にしか発火しないので、版を上げただけの利用者には何も起きない。
3. **現行の仕様に節が無いのに、コードの範囲がその仕様を指しているとき、advisory で挙げる（`trace_undeclared_impl`）。** これが欠陥D（節を消して注釈だけ残る／節を書かずに注釈だけ打った）の可視化である。合否は変えない。
4. **勘定に仕様側の三分類を足す。** 走査が走ったとき、現行の SPEC を traced（指紋を記録）・no_code（対応なしを宣言）・undeclared（節が無い）に数え、`trace_coverage.spec_coverage` として要約に載せる。無宣言への対処は、この数と第3項の advisory までとする。義務化は使用実績を見て別の ADR で裁く。
5. **自己適用**: SPEC-011 に節を足し、監査の検査一覧の範囲の指紋を記録する（自分の木にあった欠陥Dの実例を、この決定の最初の適用で解消する）。

## 帰結

- 追跡から外れる道が「無音の削除」から「読める宣言」になる。宣言の言い分と実態の食い違いは機械が指す。
- 「入れ忘れの検算」が文書側で立つ: 仕様がコードとの関係を宣言しているかは、三分類の数として毎回の監査に残る。無宣言の解消（宣言を書くか注釈を打つ）は触った所から進めるラチェットに乗る。
- 検査名が二つ増える（列挙添字の凍結が転記表・ICD・SPEC-011 の同時更新を強制する。ADR-060 の機構が最初の実戦で働く）。
- 既知の限界: 節の削除そのものは検出できない（履歴を持たない）。削除の帰結（現行のまま注釈が残る）だけを第3項が指す。三分類が数えるのは SPEC 型だけであり、API・DATA・IMPL への拡張は必要が出たときに別の ADR で裁く。
