# 検証は証拠の提示である。証跡の形だけを採り、ハザード層と過程適合は採らない

## 背景

宇宙機の搭載ソフトウェアの保証実務との対照を RESEARCH-004 に取った。取得は `curl` で行い、
本文はこちらで解析した。**最初の試みでは取得層の要約を根拠にしかけたが、それは
「LLM の文章は証拠にならない」という本体系の原則に反する。** この ADR の根拠は原文である。

一次文書に当たって出た要点は一つに尽きる。JERG-2-610C（2025年3月28日 C改訂）の用語定義は、
検証をこう定める。

> **検証** 客観的証拠を提示することによって、規定要求事項が満たされていることを確認すること
> (JERG-0-049D、ISO9000)。

さらに 6.4 検証プロセスは三つのアクティビティからなると定める ——
「(1) プロセス開始の準備　(2) 検証　**(3) 検証結果の管理**」。

**統治の体系には (3) が無い。** TEST 文書は「何をどう確かめるか」を書く。これは 6.4.1.1 の
「検証戦略の定義」に当たる。だが確かめた結果 —— どの成果物の指紋に対し、どの実行環境で、
どの版で、いつ、どの終了状態だったか —— を残す場が無い。この定義に照らせば、
**証拠を持たない TEST 文書は「検証」ではなく「検証戦略」である。**

言葉遊びではない。2026-08-02 の作業で差が出た。`_hookio.py` の実行ビットは、手元では
1036 件すべて緑で、CI では落ちた（`core.fileMode=false` により index の mode が 644）。
「試験が通った」という主張が、**どの環境の話なのかを持っていなかった**。同じ日に
「門は緑なのに実効ゼロ」を三度観測している（ADR-077 の死んだ経路・ADR-078 の機能追加を
禁じる門・ADR-080 の偽の前提）。

利用者の指摘がここに重なる —— 「グラフの接続が完全でも内容が真とは限らない。意味的正しさ、
試験環境の代表性、独立検証、仮定の妥当性、反証可能性を別に保証する必要がある」。

## 却下した選択肢

**鎖をそのまま移し、`Loss` / `Hazard` / `Safety constraint` の層を作る。**
**JERG-2-610C に「ハザード」は一度も出てこない**（全文検索で 0 回）。重要度は SW CC
（クリティカリティクラス）として一度だけ現れ、その用途は安全性の導出ではなく
**テーラリング**である（4.1）。ハザードの鎖はソフトウェア開発標準の側には無く、上位の
システム安全の標準が持ち、こちらへは一つの入力として届くだけである。層を作れば、
**原典にも無い層を増やす**ことになる。それは本 ADR が塞ごうとしている欠陥そのものである
（実効ゼロの欄が仕様に載り続ける）。

**ECSS / DO-178C 系の過程適合を目標に置く。** 過程の重さを払う主体が居ない。段差
（Level 2 の縮小構成）で軽さを守ってきた方針と当たる。なお SW CC から要求マッピング
マトリックスでテーラリングする形は、その段差と既に対応している（RESEARCH-004）。

**独立検証（IV&V）の体制を作る。** 独立した組織が要る。`NONGOAL-001` は既にこの類型を
引き受けないと定めている。

**ウェーバの仕掛けを今すぐ作る。** JERG はウェーバを「製作開始以降に発生した要求事項に
対する不適合につき、そのまままたは承認された方法による修理の後、受領する場合」と定める
（3.2、JMR-006 由来）。個別の不適合を承認して受領する形であり、`NONGOAL-001` の範囲宣言とは
別物である。**この差は実在するが、いま埋めるべき痛みが出ていない。** 名前を付けて残す。

**何もしない。** 欠落は実測で害を出している。放置は「見ていないものを見ていると書く」に
近づく。

## 決定

**検証の定義を、原典に合わせる。すなわち「証拠の提示を伴わない主張を検証と呼ばない」。
採るのはその形だけとし、過程・組織・ハザード層は採らない。**

採るかどうかの判定基準を一つに絞る —— **その仕掛けが、既にこの体系で実測された欠陥を
塞ぐか。** 塞がないものは、標準に載っていても採らない。

採るもの:

1. **検証結果を証跡として残す。** 「通った」という主張を、成果物の指紋・実行環境・版・
   終了状態・時刻へ係留する。係留の無い主張は「検証戦略」と呼び、「検証」と呼ばない。
   保存はしない —— この体系は導出値を保存しない（ADR-055）。証跡は走らせて作り、
   走らせた場が持つ。
2. **実効の検査を受入に義務づける。** 「文字が入っている」「配線されている」を検める門は、
   **その振る舞いが実際に起きることを一度は示す門**と対にする。片方だけの門は、
   実効ゼロの欄を通す（三度そうなった）。
3. **外部前提の失効周期を、対象の変化速度に合わせる。** `EXT-001` の `review_by` は
   実行環境の変化に追いついていない（ADR-032 の前提は `review_by` より前に偽になり、
   捉えたのは外部レビューだった）。

採らないもの（`NONGOAL-001` へ登録する）:

4. ハザード層（`Loss` / `Hazard` / `Safety constraint`）は作らない。
5. 過程標準（ECSS・DO-178C 系）への適合は目標にしない。
6. 独立した組織による検証（IV&V）はしない。
7. 意味的な正しさ・試験環境の代表性・仮定の妥当性は保証しない。**どの標準もこれを
   与えない。** 与えるのは証拠の提示を検証の定義に含める形までである。

## 帰結

- 「検証」と「検証戦略」が言葉として分かれる。TEST 文書がどちらなのかを、書いた者が
  自覚できる。
- 実効の検査という言い方で、三つの欠陥（ADR-077・078・080）が一つの類型に括られる。
  次に同じ形が出たときに気づきやすくなる。既に lens 側で同じ形を実装した（潰しの検査器が
  自分の判定器を canary で検め、Node の版・reporter・試験コマンド・対象 commit を刻む）。
- 保証限界: 証跡が在っても内容が真とは限らない。証跡は「この環境でこの成果物に対して
  この判定が出た」以上を言わない。試験そのものが弱ければ、強い証跡が弱い主張を飾る。
- 保証限界: ウェーバ（個別の不適合を承認して期限付きで受領する形）は作らない。
  `NONGOAL-001` は範囲の宣言であって、これではない。差は実在するが痛みが出ていない。
- 保証限界: ECSS 両標準の本文と JERG-0-049D 付録11（SW CC の設定基準）は未取得である。
  読めた時点で本 ADR の判断を見直す余地がある。
- 実装は本 ADR では決めない。証跡の形式・置き場・実効の検査の書き方・`review_by` の
  新しい周期は、それぞれ別に裁く。
