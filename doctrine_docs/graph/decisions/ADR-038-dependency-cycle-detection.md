# 依存の循環を監査が検出する（自己依存と多頂点循環）

## 背景

`depends_on` の循環（自己依存 A→A、多頂点循環 A→B→C→A）を、これまでリンタ・監査・ガードのいずれも検出も報告もしていなかった。走査はサイクル安全（訪問済み集合）で無限ループはしないが、「安全に無視する」だけで存在を教えなかった。自己参照は dead link 検査から明示的に除外されており（cycle 扱い）、その cycle を報告する検査が無かった。

循環は次の実害を生む（#89 で実証）。循環の全構成員は削除安全ガードの「現行の依存が残る」判定に永久に該当し、どの構成員も降格できなくなる論理的デッドロックになる。追跡性（要求→仕様→実装→テスト→決定）の階層に循環は本来あり得ず、循環の存在はモデル化誤りの兆候である。

本 ADR の起票と同時に、Wave 1 で著者自身が作った循環（`SPEC-003 → ADR-036 → SPEC-003`、`SPEC-012 → ADR-037 → SPEC-012`）を、導入した検査がただちに検出した。ADR が自分の下流 SPEC を `depends_on` し、その SPEC が ADR を `depends_on` し返す往復が原因だった。修正では、ADR→SPEC の向き（既存の ADR-024→SPEC-007 と同じ型）を残し、SPEC→ADR の余分な辺を外して、ADR の着地は本文の参照で保った。

## 却下した選択肢

- **循環を許して警告しない（従来）**: デッドロックを見えないままにする。R11（沈黙する故障の禁止）に反し、却下する。
- **error にして CI を落とす**: 導入直後の移行期に既存の循環で CI が止まると、段階導入の妨げになる。まず warn で可視化し、育ってから厳格化する。error 化は将来 ADR で判断する。
- **リンタ（単一文書）で検出**: 循環は複数文書にまたがるため単一文書検査では見えない。全件走査の監査が担う。自己依存だけは単一文書で見えるが、検査を二重化しないため監査に一本化する。

## 決定

`_depgraph.Graph.find_cycles()` を追加する。`depends_on` 端の強連結成分（Tarjan、明示スタックで再帰を使わず、グラフサイズに線形、サイクル安全）を求め、多頂点の成分と自己依存を循環として返す。索引に無い（dangling）端はたどらない（実在ノード間の循環だけを見る）。返り値は決定的（整列）。

監査に `dep_cycle` 検査（warn）を足す。多頂点循環は経路を `A → B → C → A` の形で、自己依存は `A→A` として報告する。dead link 検査の自己参照除外はそのまま（自己依存は `dep_cycle` が受け持つ）。

## 帰結

- 循環によるデッドロックが、導入時ではなく作成時（監査）に見える。
- Tarjan は線形で、per-turn ではなくセッション境界・CI の監査で走るため体感速度に影響しない。
- warn 段階のため、既存の循環を持つ導入先の CI（`--fail-on error`）は止まらない。移行後の error 化は将来判断。
- 著者自身の Wave 1 の循環を即座に検出・修正した（自己適用の証跡）。
