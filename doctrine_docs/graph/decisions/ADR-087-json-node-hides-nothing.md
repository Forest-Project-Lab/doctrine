# 問い合わせの節点は隠さない。組み立てた項をそのまま返す

## 背景

`dep-graph.py --json` の節点が `title` を返さない。**題名は必須項であり、体系が全文書に
持たせている**（`REQUIRED_KEYS_L2` の八項の一つ）。取れないのではなく、返していない。

原因は二段ある。

1. **節点を組む側が `title` を集めていない。** 組み立ては十三項を集めるが、そこに題名が無い。
2. **直列化が白名簿で八項に絞る。** 組み立てが持っている `superseded_by`・`updated`・
   `review_by`・`llm_context` も、ここで落ちる。

**白名簿には正本が無かった。** `SPEC-006` は問い合わせの戻り値を定めているが、`--json` の
節点の形をどこにも書いていない。書かれていない白名簿を、組み立てと別々に手で保つ構造に
なっていた。**そして実際にずれた** —— 組み立てが四項を足した後も、白名簿は八項のままだった。

読み手側の実害もある。`doctrine-lens` は題名を出すために、依存グラフとは**別に**上流の
フロントマター解析を呼ぶ橋を持っている（そのための潰しの表の一行まで在る）。
題名がグラフから来ないことが、読み手に二本目の経路を作らせていた。

## 却下した選択肢

**白名簿へ `title` を足すだけにする。** いま落ちている一項は塞がるが、**構造は残る**。
組み立てが次に項を足したとき、また落ちる。同じ欠陥をもう一度作る。

**節点の形を `SPEC-006` に書き、白名簿を手で保つ。** 正本はできるが、二箇所を人が
一致させ続ける形は変わらない。ずれたときに気づく手立てが無い。

**節点を丸ごと返すのをやめ、問い合わせごとに必要な項だけを返す。** 読み手が何を要るかは
読み手が決める。こちらが先に絞ると、絞りの是非を巡って毎回この issue が立つ。

## 決定

**問い合わせの節点は、組み立てた項をそのまま返す。隠さない。**

1. 組み立てが `title` を集める。必須項なので必ず在る。
2. 直列化の白名簿を廃す。組み立てが節点へ入れた項は、すべて返す。
3. ただし `depends_on` と `impacts` は、生のフロントマターの値ではなく**索引の値**を返す
   （既にそうなっている。解決済みの端であり、こちらのほうが読み手に有用である）。この一点だけ
   は例外として `SPEC-006` に明記する。
4. **節点の形を `SPEC-006` に書く。** 白名簿の正本をここに置く。
5. **組み立てと直列化の項が一致することを受入で凍らせる。** これが本当の歯止めである ——
   一致を機械が見ていなければ、正本を書いてもまたずれる。

## 帰結

- 題名がグラフから来る。読み手が二本目の経路を持たなくてよくなる（`doctrine-lens` の題名の
  橋は、これで不要になりうる。あちらの判断であり、こちらでは変えない）。
- `updated`・`review_by`・`superseded_by`・`llm_context` も来る。鮮度と後継を読み手が
  自分で判じられる。
- 項を足したときに落ちる構造が消える。組み立てへ足せば返る。
- 保証限界: 加える項が増えれば投影も増える。大きな木では応答が重くなりうる。いま測って
  いないので、重くなったら絞る方法（問い合わせでの選択）を別に決める。**先に絞らない。**
- 保証限界: これは投影の形の変更である。既存の読み手が「八項しか来ない」ことに依存して
  いれば影響する。項の追加なので壊れる読み方は限られるが、**破壊的でないとは言い切らない。**
