# 監査要約も測った木の版を名乗る — あわせて root の意味と findings の項目形を宣言する

## 背景

graph の読み口が測った木の版と作り手を名乗ることになった（ADR-155。issue #294 の受け。
権限は ADR-151）。監査要約（`docs-audit/1`）だけが名乗らないままだと、三口の返す値を
合成する消費者は「同じ木を測ったか」を監査要約についてだけ照合できない。あわせて
ICD-005 の宣言に二つの穴がある: (1) `root` の欄は列挙されているが意味が無い —— 実装は
絶対パスに正規化して書く（SPEC-011。注入側が相対 root を照合不能として捨てるため）のに、
追跡索引の `root` は名前だけであり、読み手には同じ名前の欄が逆の意味を持つ理由が
見えない。(2) `findings` の各項の鍵は実装にしか無く、所見単位で読む消費者は宣言なき形を
読むことになる。各ドメインの入口はそのドメインの ICD が持つ（ADR-137 の原則）ので、
監査側の宣言は本決定で行う。

## 却下した選択肢

- **`root` の意味を追跡索引に合わせて名前だけへ変える。** 既知の鍵の意味を変える互換破壊で
  あり（確定事実13）、注入側の照合（他プロジェクトの所見の誤注入を捨てる）が壊れる。
  どちらの `root` も故意の設計であり、揃えるのではなく意味を宣言する。
- **木の同一性の照合を `root` に担わせる。** 名前だけの `root` と絶対パスの `root` は
  照合の鍵になれない。同一性は `source_revision` の同値で照合する（ADR-155）。
- **findings の項目形は実装任せのままにする。** 監査要約で一度直した形（宣言なき消費。
  ADR-137 の背景）が所見の粒度で残る。

## 決定

1. `docs-audit/1` の最上位に `source_revision`・`source_dirty`・`generator` を足す。意味は
   ADR-155 の定義をそのまま使う（本ドメインで再定義しない）。鍵の追加は互換である
   （確定事実13。ADR-152）。
2. ICD-005 のデータ契約に `root` の意味を一行で宣言する: 絶対パスに正規化して書く。
   理由は注入側の照合（SPEC-012）であり、追跡索引の `root`（名前だけ）とは問いが違う。
   木の同一性の照合には `source_revision` を使う。
3. ICD-005 に `findings` の各項の形を宣言する: `{check, severity, doc_id, path, message, refs}`。
   `severity` の語彙は error・warn・advisory（重大度の正本は従来どおり本 ICD の検査表）。

## 帰結

- 三口（依存グラフ・追跡索引・監査要約）の返す値がすべて測った木の版を名乗り、消費者は
  返る値だけで合成の整合を検められる。
- 追跡の所見の重さを問う消費者への答えがこの宣言で閉じる —— 判定済みの重さは監査要約の
  `findings`（`trace_stale` ほか trace 系の検査）から severity 付きで読める。追跡索引そのものに
  重さは足さない（検出に徹し判定はしない。ICD-002 の規律）。
- 保証限界: 版の鍵は「いつの木か」を言うだけであり、要約の内容の解釈が利用者側に残る
  ことは ADR-137 から変わらない。
