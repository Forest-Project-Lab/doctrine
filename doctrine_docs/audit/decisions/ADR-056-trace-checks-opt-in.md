# 追跡の検査は、仕様が指紋を記録したときだけ効く（黙って始まり、黙って終わる）

## 背景

段4 で、コードと仕様の追跡を監査の検査として足す。素朴に「現行の SPEC に対応する注釈が一つも無ければ挙げる」と書くと、この体系では即座に 26 件の所見が出る（注釈を打ったのは 1 件だけ）。既に運用しているリポジトリへ入れれば、もっと多く出る。

導入した初日に大量の警告を浴びせる形は、近縁の道具が繰り返し踏んでいる失敗である。人は警告を読まなくなり、機能を切る。切られた機能は何も守らない。

もう一つ、費用の問題がある。追跡の検査を無条件で走らせると、監査のたびにコードの木を走査することになる。この体系では 0.43 秒だが、規模の大きいリポジトリでは無視できない。**追跡を使っていない利用者が、使っていない機能の費用を払う**のは筋が通らない。

さらに、注釈は任意である（ADR-054 の既知の限界: 印を打っていないコードは追跡の外）。したがって「根拠を持たないコード」を挙げることは原理的にできない。挙げられるのは、注釈が指す先の不備と、記録した確認との食い違いだけである。ここを取り違えて「全てのコードに根拠を要求する」形にすると、達成できない要求を掲げることになる。

## 却下した選択肢

- **全ての現行 SPEC に注釈を要求する**: 導入初日に大量の所見。達成できない要求（注釈は任意）。仕様には、そもそもコードを持たないもの（手順・方針）がある。
- **設定で on/off を切り替える**: 切り替えの状態が体系の外（設定ファイル）に出る。どの仕様が追跡されているかを、文書を見て判じられなくなる。
- **注釈の存在を起点にする（コード側から opt-in）**: 注釈を消せば検査も消える。実装を消したときに仕様側の期待が残らず、下向きの不在（仕様はあるが実装が無い）を永久に検出できない。

## 決定

**追跡の検査は、仕様の文書が指紋を記録したときだけ効く。** 記録の有無が、そのまま opt-in の印である。

1. 仕様の文書に `## 実装の指紋` の節があり、`- sha256:<64桁>` の行を持つとき、その仕様は追跡の対象になる。節が無ければ、その仕様について何も検査しない（黙る）。
2. **どの仕様も節を持たないときは、コードの走査そのものを行わない**。使っていない機能の費用を払わせない。
3. 起点を仕様の側に置くのは、注釈を消したときに期待が残るようにするためである。コード側を起点にすると、実装を消した瞬間に検査も消え、不在を検出できない。
4. 挙げるのは次の五つに限る。「根拠を持たないコード」は挙げない（注釈は任意であり、原理的に判じられない。ADR-054 の既知の限界）。

| 検査 | 意味 | 重大度 |
|---|---|---|
| `trace_mark_error` | 印の対応付けの誤り（入れ子・両端の id の不一致・閉じ忘れ・開いていない end・空の範囲） | error |
| `trace_broken_ref` | 注釈が実在しない id を指す | error |
| `trace_deprecated_ref` | 注釈が廃止・置換済みの id を指す | warn |
| `trace_stale` | 記録した指紋と、導出した指紋が食い違う | warn |
| `trace_missing_impl` | 指紋を記録した仕様に、対応する範囲が一つも無い | warn |

`trace_mark_error` を error にするのは、印の対応付けの誤りが**機械で判じきれる欠陥**だからである。これを機械で捕まえられることが、構文解析器ではなく注釈を選んだ根拠だった（ADR-054 の帰結）。ここを緩めると方式の前提が崩れる。

## 帰結

- 導入しても何も起きない。追跡を使いたい仕様に節を書いた分だけ、検査が効く。段階的に増やせる。
- 使っていないリポジトリでは走査が走らない。費用がゼロである。
- 仕様の側が起点なので、実装を消しても期待が残り、不在を検出できる。
- 節を書く手間が opt-in の対価になる。手で書き写す誤りを減らすため、指紋の行を出す形（`trace-index.py --format fingerprints`）を用意する。
- 既知の限界: 根拠を持たないコードは挙げられない。どの仕様が追跡されるべきかの判断は人に残る（NONGOAL 第1項と同じ形）。節を書き忘れた仕様は、黙って追跡の外にある。
