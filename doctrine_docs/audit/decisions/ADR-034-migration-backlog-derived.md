# 移行の台帳は分類の記録から導出し、二重の台帳を持たない

## 背景

成熟したリポジトリへ途中から doctrine を入れると、統治木の外に .md が大量に残る。整理は一度きりの号令では続かず、進捗が見えないまま風化する(Issue #60)。一方で「移行バックログ」という新しい台帳ファイルを作ると、分類の記録(`_system/.md-intake`、ADR-021)と二重の正本になり、体系が自分で禁じた重複を自分で犯す。

## 却下した選択肢

- 専用のバックログファイルを新設する: `.md-intake` と二重の台帳になる。どちらが真かを機械で判別できなくなる(R8)。
- 一括の移行だけを提供する: 中断で風化する。進捗の記録が無く、再開の地点も分からない。
- 何もしない(監査の助言のみ): 助言 50 件の一覧は行動に変換されず、壁紙化する(実際に起きていた)。

## 決定

移行のバックログは保存せず、毎回導出する。未分類の一覧は監査(`stray_document` の「未分類」所見)から、分類済みの数は `.md-intake` の行数から引く。進捗の正本は `.md-intake` だけである。表面化は 1鼓動1件: `gov-heartbeat.py` が、より重い義務(死活・定例)がすべて静かなときにだけ、未分類の先頭 1 件を自己完結の文で促す(統治率 X/Y を添える)。SessionStart の注入は未分類の残数を統治率として常時表示する。

## 帰結

- 分類が 1 件進むたびに、次の鼓動で数が減って見える。中断しても台帳が真実を保ち、再開は自動で続きから。
- 優先順(どれから分類するか)の高度化(被参照・git の活動量)は判断であり、docs-curate の手順(external-md-intake)に委ねる。機械の並びは決定的(整列)に留める。
- 台帳を消せば統治率も消える。移行の状態は `.md-intake` 以外のどこにも無い。
