# 配布技能に system-map-draft を加える（ADR-010 を置換。一覧の正本は SPEC-016）

## 背景

doctrine-lens の System Map（Phase 2。issue #212）は、意味モデルの下書きを自動で起草する
道具を doctrine 側の領分と定めた（書き込みを持つ画面は Lens ではない —— 合意台帳 v3.2-4）。
起草は LLM の仕事であり、体系側が持てるのは手順と門である。技能（SKILL.md による手順の
配布物）はそのための形をすでに持つ。

一方、ADR-010 は「技能は7つに固定する」と定め、DECIDED-001 事実8 がそれを写している。
数の固定は「役割の重複を作らない」ための手段だったが、固定そのものが正本になると、
新しい領分（意味モデルの起草）が現れたときに根拠ごと置き換える道しかない。それが本 ADR
である。所有者は 2026-08-07 の会話で、生成器を配布 8 個目の技能として出すことを裁定した。

## 却下した選択肢

- **開発レーンの技能にとどめる**（assurance-loop と同じ扱い）。実験段階の位置づけとは
  整合するが、生成器の利用者は doctrine を導入した各リポジトリであり、開発レーンに
  置くと配布されず届かない。所有者裁定が配布を選んだ。
- **技能ではなくスクリプトにする**。起草は意味の読み取りを要し、決定論のスクリプトでは
  書けない。スクリプトが持つのは出所の機械検証（門）だけで足りる。
- **数の固定を維持して既存技能へ相乗りさせる**。docs-curate や doc-author の役割と
  重ならない新しい領分であり、相乗りは ADR-010 自身が却下した「役割の重なり」を生む。
- **何もしない**。#212 の分担合意に doctrine 側が応えない状態が続く。

## 決定

1. **配布技能に `system-map-draft` を加える。** 役割は、対象リポジトリから proposed 限定の
   意味モデル（lens 側の検証用スキーマ 0.1）を起草すること。確定（confirmed への昇格）は
   人の仕事のまま。
2. **技能の一覧の正本は SPEC-016 とし、増減は根拠 ADR の置換によってのみ行う。**
   数そのものを確定事実に固定しない（DECIDED-001 事実8 は本 ADR を根拠に言い直す）。
3. **起草の規律**: 起草者は対象リポジトリの文書・コード・履歴を直接読んでよい。ただし
   `.claude/.cache` は読まない（導出された事実は宣言済み CLI から取る。ICD-002・ICD-005）。
   依存グラフの辺を Flow へ自動変換しない。全ての値は `review_status: proposed` で、
   全ての値に出所（読んだ場所・確認日・判定）を持たせ、出所は機械検証を通す
   （捏造出所ゼロが検収の門）。
4. **ADR-010 の残る二決定は現行のまま引き継ぐ**: ドメインのフォルダと各層は、その型の
   文書を最初に書くときに `doc-author` がそのつど生成する（遅延生成）。§1 の語彙は
   テンプレート（`glossary.md.tmpl`）が一度だけ書き写し、用語チェッカーはそれを運用版と
   して読む（辞書の単一符号化）。

## 帰結

- SPEC-016・TEST-016・IMPL-016・authoring の ICD・DECIDED-001 事実8・公開ビュー・
  `spec/doctrine.ja.md` §4.1 の技能の数の記述を一覧参照へ改める（CHANGE-008・IMPACT-008）。
- 保証レーン（assurance）を配布技能にしない判断（ADR-114 の却下）は本決定の後も成り立つ
  —— 根拠は「7 個固定」ではなく「開発専用の領分は配布境界の外」に置き直す。
- 本決定は System Map 画面の製品採用・正式移管・doctrine スキーマの変更のいずれでもない。
  doctrine の型・必須キーは増えない（ADR-112 のスキーマ不変は維持）。lens 側の H 層は
  `UNASSESSED`（未評価）のままであり、移管の裁定は別途の所有者判断である。
- 保証限界: 起草の意味の正しさは保証しない（全値 proposed。昇格は人）。機械が検めるのは
  出所の実在と形だけである。
