# 雛形の指示文が残ったフロントマターを咎める。判定は形で行い、雛形を読まない

## 背景

雛形は、埋めるべき値を山括弧の指示文（`<個人名>`・`<YYYY-MM-DD>`・`<決定の主題>`）で置く。
**埋め忘れても、どの検査にも掛からない。** 必須キーの検査は「鍵が在るか」を見ており、
「値が指示文のままか」を見ていない。

**報告は実害を挙げている** —— 呼び手の木で、`canonical_for: [glossary]` を持つ用語辞書の
正本に `owner: <記入>` が初期化から残っていた。そのあいだにその木は決定を 20 本書き、
監査は一貫して error 0 だった。**人も機械も気づかなかった。**

こちらでも再現した。題名・責任者・更新日・出所をすべて指示文にした仕様を書いて、
ファイル単位のリンタに掛けた。

```text
リンタの所見: (無し)
```

**一件も出ない。** 測った結果を並べる。

| 測ったこと | 結果 |
|---|---|
| 雛形の数 | 21 種 |
| 山括弧の指示文 | 191 箇所 |
| フロントマターでの形 | **値の一部でもある**（`id: ADR-<連番>` のように） |
| **いまの木のフロントマターの値に山括弧を含むもの** | **0 件** |
| 節点に無い必須キー | **`owner`**（必須キー8個のうち、集めていない最後の一つ） |

最後の行が効く。**報告が壊れていたと言うのは、まさに `owner` である。** そして題名
（ADR-087）・出所（ADR-097）に続いて、**必須キーを集めていない三件目**である。

**出所も測った。初期化したての木を作って監査に掛けると、8 件が挙がる。**

| 文書 | 指示文が残る項 |
|---|---|
| `DECIDED-001` | `title`・`owner`・`sources`・`canonical_for` |
| `GLOSSARY-001` | `owner`（**報告が見つけたのはこれである**） |
| `NONGOAL-001` | `owner` ほか |

つまり報告の `owner: <記入>` は、**初期化の瞬間に生まれて、そのまま残っていた**。
そして体系は「初期化直後のコーパスは監査の所見ゼロで通る」を凍結していた。
**その緑は偽りだった** —— 用語辞書の正本に責任者が居ないまま緑だったのである。

## 却下した選択肢

**雛形から判定を引く（報告の提案）。** ADR-090 が**同じ案を却下している** —— 雛形は
配布物であり、導入先で差し替えられる。正本が動くものになると、検査の意味が木ごとに
変わる。確定事実1（構造規則はコードの中に一度だけ）と当たる。**同じ理由で断る。**

**山括弧を含む値をすべて咎める（本文も見る）。** 本文には `<svg>` のような山括弧も、
置き場所の記法（`<domain>/`）も、id の書式（`<TYPE>-<NNN>`）も正当に出る。
**誤検知が多すぎる** —— 報告自身がそう書いている。**フロントマターに限る。**

**指示文の語彙の表を持つ（`<記入>`・`<個人名>`…）。** 雛形が語を増やすたびに表が古びる。
**形で判ずれば表が要らない** —— 山括弧の形そのものが指示文の印である。しかも実測で、
いまの木のフロントマターに山括弧を含む値は一件も無い（誤検知の余地が無い）。

**ファイル単位のリンタだけに置く。** **報告の木では捕まらない** —— 呼び手の門は監査だけを
回しており、全件のリンタを回していない（doctrine-lens#12 で別に報告した）。
報告された実害が直らない置き方はしない。

**全件監査だけに置く。** 書いた瞬間には言われない。予防の層が空く。

## 決定

**フロントマターの値に雛形の指示文が残っていたら咎める。判定は形で行い、雛形を読まない。**

1. **判定を共有コアに一度だけ置く**（`_frontmatter` の公開関数）。フロントマターの値
   （一覧の要素を含む）に山括弧の形が含まれていたら、指示文とみなす。
   **雛形も語彙の表も読まない。**
2. **ファイル単位のリンタが誤り（error）を出す**（予防の層）。
3. **全件監査も誤り（error）を出す**（検出の層）。**判定は同じコアを呼ぶ**（ADR-053・
   ADR-024 と同じ形）。ただし**見る入力は同じではない** —— リンタはフロントマター全体を
   見るが、監査は節点が運ぶ項だけを見る。必須キー8個と鮮度の項は覆うが、`created` は
   必須キーではないので節点に無く、監査は見ない。
4. **本文は見ない。** 正当な山括弧が出るからである（上記）。
5. **節点に `owner` を足し、必須キー8個がすべて節点に在ることを凍らせる。**
   集めていない必須キーはこれで三件目であり、**四件目を作らない。**
6. **初期化したての木の約束を改める。** 凍結を「監査の所見ゼロで通る（緑）」から
   「**人が埋める箇所だけを名指しして赤い**」へ変える —— 指示文以外の所見は一件も
   出ないこと、指示文の所見は `_system/` の正本に限ること、の二つを凍らせる。
   **埋まっていない正本を健全と呼ばない。** 初回の体験は「三つの正本の題名と責任者を
   書け」という名指しになる。

## 帰結

- 初期化した木が、埋め忘れたまま緑になることが無くなる。責任者・題名・日付が指示文の
  ままでは通らない。
- 呼び手の木でも効く（監査の層に在るので、全件のリンタを回していない木でも捕まる）。
- **初期化したての木は緑ではなくなる。** 三つの正本の欄を埋めるまで門は赤い。これは
  一度きりで、直す先を名指しする所見であり、**門が邪魔者になる形ではない**と判じた
  （ADR-090 が「門が邪魔者になれば切られる」を戒めた基準に照らした）。
- 保証限界: **見るのは形だけである。** 指示文を消して別の無意味な値（`x` など）を
  入れれば通る。**埋まっていることは、正しいことではない。**
- 保証限界: **本文の指示文は見ない。** 節の中身が雛形のままでも咎めない。
- 保証限界: 山括弧を含む正当な値を将来フロントマターへ書きたくなったら、この検査と当たる。
  いま 0 件なので取引として受ける（当たったときは、そのとき決め直す）。
- 保証限界: **二つの層が見る範囲は同じではない。** 判定のコアは一つだが、リンタは
  フロントマター全体を、監査は節点が運ぶ項だけを見る。`created` はリンタだけが咎める
  （必須キーではないので節点に無い。確定事実3）。**同じ入力に同じ答えを返す**ことは
  保証するが、**同じものを見ている**とは主張しない。
- 保証限界: **日付の形は別の問題である。** `updated: 2026-13-45` は指示文ではないので、
  この検査では通る（実測。別に起票する）。
