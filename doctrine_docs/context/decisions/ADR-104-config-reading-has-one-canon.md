# 統治の設定の読み取りを共有コアに一度だけ置く

## 背景

`_system/.context-config.json` を読む実装が、**五箇所に別々に在った。** この一枚は
常時投入の上限（確定事実6）・パックの上限・追跡の悉皆の様式・走査の適用除外を握る
（ADR-096 で指紋の見張りを付けた、あの一枚である）。

**そして一つだけ違う答えを返していた。** 同じ内容を BOM 付きと BOM なしで書いて測った。

| 読み手 | BOM なし | **BOM 付き** |
|---|---|---|
| `docs-audit` | `trace_mode` を読めた | **`None`（既定へ落ちた）** |
| `gov-heartbeat` | 読めた | 読めた |
| `inject-contract` | 読めた | 読めた |
| `collect-context` | 読めた | 読めた |
| `trace-index` | 読めた | 読めた |

`docs-audit` だけが `utf-8` で開いており、他の四つは `utf-8-sig` だった。**BOM を
一つ付けるだけで、監査が設定を丸ごと見失う。**

害は静かである。

- `trace_mode: "exhaustive"` が無視され、**印なしの残高の警告が黙って消える**
  （警告が消えたことは、警告では分からない）。
- 調整値が既定へ戻る。**閾値を下げていた木で、所見が静かに減る。**
- 鼓動はまだ `exhaustive` を見ているので、**二つの読み手が木の様式について食い違う。**

これは ADR-053 が防ごうとした形そのものである —— あちらは「要約の読み取りを共有コアに
一度だけ正本化する」と決めた。**設定の読み取りには同じ手が入っていなかった。**
日付の解釈（ADR-099）とスカラへの正規化（ADR-101）に続いて、**同じ類型の三件目**である。

**もう一つ、読み方の門を通っていない。** 確定事実12 と ADR-075 は「統治対象を読む前に
通常ファイルかを検める」と定め、そのために共有の読み手（`read_text`）を置いた。
五つの設定の読み手はどれもそれを通らず、素の `open` を使っている。
**ADR-075 が名指した類型（名前付きパイプ・デバイスを開いて戻らない）と同じ面である。**

## 却下した選択肢

**`docs-audit` の符号化だけ直す。** 五つ揃うが、**六つ目が生まれたときに同じことが起きる。**
実際、数え始めたときは四つだと思っていた —— 五つ目（`trace-index`）は探して初めて出た。
**数え漏らしが起きる形そのものが問題である。**
今日すでに二度（日付・正規化）、写しが「一箇所だけ直る」事故を起こしている。

**緩い側へ揃える（全部 `utf-8`）。** BOM 付きの設定が誰にも読めなくなる。
編集器が BOM を付けるのは普通にある。**厳しい側とは「より多く読める側」である。**

**各呼び手の調整値の意味まで正本へ寄せる。** 監査は型を検めて写し、注入は上限を解決し、
パックは別のキーを見る。**受け持ちが違うものを一つにすると、どの既定が誰のものか
分からなくなる。** 正本は**読み取りと解析**だけを持つ（ADR-053 と同じ切り方 ——
あちらも候補順と照合だけを持ち、使い方は呼び手に残した）。

**そのままにして食い違いを文書に書く。** 書いても消えない。ADR-053 が一本化を決めた後に、
その中で五本が残り続けたのが現状である。

## 決定

**統治の設定の読み取りを共有コアに一度だけ置く。写しは全て正本を呼ぶ。**

1. **`_config.py` を置き、そこが正本とする。** 道の解決（`<docs-root>/_system/.context-config.json`）と
   読み取りを持つ。**共有の読み手を通す**ので、通常ファイルでなければ開かない（ADR-075）。
   BOM を落とす（`utf-8-sig`）。写像でなければ空の写像を返す。**決して例外を投げない。**
2. **五つの写しを消し、呼び手は正本を呼ぶ。** 薄い前面も置かない（ADR-099・ADR-101 と
   同じ理由 —— 前面は後からそこで挙動を変えられる場所になる）。
3. **調整値の意味は呼び手に残す。** 監査の型の検め、注入の上限の解決、パックのキーは
   そのまま。正本が持つのは読み取りだけである。
4. **機械が二重定義を咎める。** 設定を自前で開くスクリプトが現れたら、メタの受入が落ちる
   （手で書いた表で凍らせる。ADR-099・ADR-101 と同じ形）。
5. **厳しい側へ揃えるのではなく、多く読める側へ揃える。** BOM 付きも読む。

## 帰結

- 設定についての答えが、読み手によって割れなくなる。ADR-053 の一本化が設定にも届く。
- 通常ファイルの門が設定の読み取りにも掛かる（ADR-075 の面が一つ埋まる）。
- 保証限界: **揃えるのは「読めるかどうか」だけである。** 値の妥当性は呼び手が判ずる
  （監査は型を検め、注入は上限を解く）。**正本は値を検めない。**
- 保証限界: 設定が読めないときは空の写像になる。**「無い」と「壊れている」を区別しない**
  —— 呼び手はどちらでも既定へ落ちる。区別が要る場面が出たら、そのとき決め直す。
- 保証限界: 機械が咎めるのは「設定の道を自前で開く」形である。別の書き方をすれば掴めない。
- 保証限界: **通常ファイルの門が効くことは、振る舞いでは測っていない。** 名前付きパイプで
  戻らないことを測ろうとすると試験が止まる。**測れないものを測ったふりにしない** ——
  代わりに「共有の読み手を呼んでいること」と「素の `open` を持たないこと」を構造で
  凍らせた（ディレクトリを置く試験は頑健さの検めであって、門の証明ではない ——
  素の `open` でも同じく黙ることを実測した）。
