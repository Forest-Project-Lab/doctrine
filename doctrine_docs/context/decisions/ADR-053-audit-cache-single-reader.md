# 監査要約の読み取りを一箇所に正本化し、木の世代をまたいだ要約は捨てる

## 背景

導入・再導入のシナリオを実測して、二つの欠陥が出た。

一つ目。統治木を消して同じ場所に作り直したとき（一度入れて外し、また入れた）、前の世代の監査要約が `.claude/.cache/` に残る。要約の `root` は同じ絶対パスなので照合を通る。結果、一度も監査していない新しい木に対して、セッション開始の契約が「前回監査: error 0 / warn 0 / advisory 0」と告げ、鼓動も黙る。実測では、新しい木が実際には error を持っていてもそうなった。統治の生存性（`[R11]`）が禁じている「沈黙する故障」に、正の健全信号まで添える形である。木の同一性は場所では決まらないのに、場所だけで照合していた。

二つ目。要約を読む二人（注入と鼓動）で、判定の段が揃っていない。鼓動は候補を選ぶ段で `schema` を照合し、合わない候補を飛ばして次の候補へ進む。注入は候補を選んでから要約を組む段で `schema` を見るため、最初の候補が未知のスキーマだとそこで止まり、後ろの正しい候補へ進まない。両者の説明文はどちらも「読者間で判定を揃える」と書いているが、実装は揃っていない。同じ問い（どの要約を読むか）に対する答えが体系内に二つある状態で、ADR-049 で直した重複 id と同じ形の欠陥である。

## 却下した選択肢

- **scaffold が古い要約を消す**: 書き込みで直すのは、非破壊（既存を上書きしない）の約束に例外を作る。要約は統治木の外にあり、scaffold が持ち場を越える。読み手側で捨てるほうが、約束を曲げずに済む。
- **要約に木の識別子（乱数）を持たせる**: 新しい機構が増える。識別子の生成・保存・照合を足すより、既にある `initialized` の日付で世代を判じるほうが小さい。
- **一つ目だけ直す**: 読み取りが二箇所にあるかぎり、片方だけ直せば判定はさらに割れる。二つは同じ根（読み取りの規則が正本化されていない）から出ている。

## 決定

要約の読み取りを、共有コア `_auditcache.py` に一度だけ正本化する。注入と鼓動は、これを呼ぶ。自前の候補順・照合を持たない。

読み取りの規則は次の順で、一つでも満たさない候補は**飛ばして次の候補へ進む**（そこで止まらない）。

1. 候補順は、プロジェクトスコープ → 作業ディレクトリ → 旧プラグイン配置（ADR-037 のまま）。
2. `schema` が `docs-audit/1` であること。
3. `root` が絶対パスで、読み手の統治木と同じ場所を指すこと。
4. **世代の照合**: 統治木の `_system/.governance-state` に `initialized` の日付があり、要約の日付がそれより**厳密に古い**とき、その要約は前の世代のものとして捨てる。

`initialized` を持たない木（この決定より前に作られた木）では、世代の照合をしない。判じる材料が無いためであり、挙動はこれまでと変わらない（前方寛容。ADR-042）。

## 帰結

- 作り直した木に、前の世代の健全さが引き継がれなくなる。要約が捨てられた後は「前回監査なし」へ倒れ、`initialized` があるので導入直後の中立の案内になる（ADR-041）。誤った安心を与えず、初日を警告でも始めない。
- どの要約を読むかの答えが一つになる。未知のスキーマの候補が先にあっても、後ろの正しい候補へ進む。
- 既知の限界: 世代の照合の粒度は日である。木を消して同じ日に作り直し、その日のうちに前の世代の要約が残っていた場合は、日付が等しいので捨てられない。窓は一日で、再導入は稀な操作であるため、この残余は受け入れる。狭めるには要約側に世代の識別子が要り、それは新しい機構になる。
