# 三つの保証限界（サブエージェント注入・id の改名・採番の衝突）を非目標として明文化する

## 背景

先行事例の調査（RESEARCH-003）と自前の実測で、体系が保証しないのに保証しているように見えうる箇所が三つ残っていた。見ていないものを見ていると読まれる状態は、限界の明示より害の大きい誤った安心を与える（ADR-050 と同じ判断）。三つとも、対策の実装ではなく境界の明文化を先に行う。

1. **サブエージェントへの契約注入。** SessionStart の注入は主セッションにしか届かない。作業を分岐した子エージェントは、契約の復唱も確定事実も持たずにツールを呼ぶ。先行事例では、規範が子に無言で継承されない故障が実運用で報告されている（RESEARCH-003 類型6）。ガード（PreToolUse/PostToolUse）は子のツール呼び出しにも効くが、それは拒否の面であって理解の面ではない。
2. **id の改名・改番。** 体系は履歴を持たない（git を呼ばない。DECIDED-001 事実7 の帰結）。内容の指紋はファイルの移動を生き延びるが（ADR-055）、id そのものの改名は「別の文書が現れ、元の文書が消えた」ようにしか見えない。先行事例でも、被参照を保った改名はどの道具も未解決だった（RESEARCH-003 類型3）。
3. **採番の衝突。** 連番の id をブランチ並行で振れば、同じ番号が二重に生まれる。防止には採番の中央装置が要り、それは分散の版管理と根本で衝突する（RESEARCH-003 類型4 — 先行事例の解決案は採番サーバへ後退した）。

## 却下した選択肢

- **サブエージェント起動時の注入を実装する**: ハーネスの子エージェントは SessionStart を通らず、注入の差し込み口が無い。呼び出し側が文脈を持ち込む道（llm-context-pack）が既にあり、機構の追加は差し込み口が生まれてから裁く。
- **id の別名表（旧 id → 新 id）を持つ**: 表は第二の正本になり、表と実体の食い違いという新しい欠陥面を作る。正規の道（後継を作って置換し、依存元を張り替えてから降ろす）が既にあり、逸脱だけが問題になる。
- **採番を予約式・乱数式にする**: 予約は中央装置を要し、乱数は id の可読性（型と番号で引ける）を壊す。衝突の事後検出（採用規則と影の error。ADR-049）で十分に痛みが小さい。
- **何も書かない（暗黙の限界のまま残す）**: 三つとも「保証されている」と誤読された実例が先行事例にある。境界は正本に書く。

## 決定

**横断のやらないこと（NONGOAL の正本）に三項を足し、これを保証限界の記述とする。**

1. サブエージェントへの契約注入はしない（届かない）。ガードは子のツール呼び出しにも効くが、契約の理解は主セッションの受け持ちであり、子へ渡す文脈は呼び出し側が組む（llm-context-pack）。
2. id の改名・改番は追わない。変更の正規の道は「後継を作って置換し、依存元を張り替えてから降ろす」であり、旧 id を指し続ける参照は監査（dead link・trace_broken_ref）が事後に指す。
3. ブランチ並行の採番の衝突は防がない。事後に採用規則（先勝ち。ADR-049）で一意に裁き、影は error で名指しする。

## 帰結

- 保証の地図が閉じる: 何を守り（ガード・監査・勘定・印）、何を守らないか（本 ADR の三項＋既存の非目標）が、すべて正本に並ぶ。
- 利用者への実害の緩和がそれぞれ明文になる: 子には文脈を持ち込む、改名は置換で行う、衝突は監査が指す。
- 既知の限界: 三項とも「痛みが大きくなったら決め直す」対象である（ADR-057 と同じ形）。特にサブエージェント注入は、ハーネスに差し込み口が生まれた時点で再検討する。
