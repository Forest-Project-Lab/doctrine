# 意味モデルの型 MODEL（系の意味モデルを持つ文書の型）の設計

## 背景

ADR-161 が方向を決め（正本は統治木の中の型付き .md、JSON は一方通行の投影）、ADR-162 が
器の凍結を解いた。ADR-161 の保証限界は「型の名前・必須キー・必須節の中身は決めていない。
それらは実施の日の設計であり、根拠 ADR を要する」と書いた。本 ADR がその設計である。

描く先の器は、doctrine-lens 側の検証用スキーマ `system-map/gold-model/0.1` である。最上位に
八つの欄（`schema`・`target`・`system`・`elements`・`flows`・`contracts`・`scenarios`・
`anchors`）を持ち、各実体は `id` と型ごとの必須欄、出所の配列 `provenance`、
`review_status` を持つ（形の手引きは `plugin/skills/system-map-draft/references/model-shape.md`）。
値の数は小さくない（実測: doctrine を対象にした下書きで出所 38 件）。

統治の型は .md とフロントマターを前提にしている（必須キーは八つ。ADR-033）。本文で構造を
担保する道具として体系が既に持つのは、型ごとの必須節（ADR-090）とリンタの点検である。
あわせて、体系は標準ライブラリだけで動く（DECIDED-001 事実7）。JSON は標準ライブラリで
読めるが、YAML の解析器は持たない。

## 却下した選択肢

- **本文を表で書き、列を検める。** 読みやすいが、実体ごとに欄の数と型が違い、出所は入れ子の
  配列である。表へ収めるには入れ子を独自の記法で潰すことになり、その記法の解析器を新しく
  書くことになる。器への忠実さと引き換えに壊れ方が増える。
- **本文を YAML の塊で書く。** 解析器を持たない（pip を使わない。DECIDED-001 事実7）。自前で
  書けば部分実装になり、フロントマターの解析器と同じ罠を二つ目に増やす。
- **文書ごとに一つの大きな JSON の塊にする。** 人が読むものが JSON 一枚と変わらず、.md へ
  移す意味が薄い。差分も実体ごとに読めない。
- **型を作らず DATA 型を流用する。** DATA の必須節は「エンティティ・保存方針・保持期間」で
  あり、意味が違う。型の意味を曲げると、既定の位置づけ・点検周期・置き場所まで一緒に曲がる。
- **JSON を統治木へ置き、.md から参照だけする。** 正本が二つになる（ADR-161 が却下済み）。

## 決定

1. **型の名前は `MODEL` とする。** 置き場所は `<domain>/model/`、id は `MODEL-<連番>`、
   ファイル名は `MODEL-<連番>-<短い名>.md`。（`model` ドメインの中に置くと
   `model/model/` になるが、そこは体系の構造規則を持つドメインであり、系の意味モデルを
   書く用は無い。名の重なりを理由に型の名を曲げない。）
2. **必須節は六つとする**——「系の概要」「要素の一覧」「流れの一覧」「契約の一覧」
   「シナリオの一覧」「アンカーの一覧」。器の最上位の欄と一対一に対応させる
   （`schema` と `target` は「系の概要」の塊が持つ）。**節名に裸の一般語を使わない。**
   節名は用語チェッカーの照合から外れる（書き手が言い換えられないものを咎めない。
   ADR-135）ので、「流れ」のような一語を節名にすると、その語を禁止同義語に持つ木で
   照合が黙って落ちる。複合語にして射程を狭める。
3. **実体は一つにつき、一つの `###` 見出しと、その直下の JSON の塊（```json の囲み）で
   書く。** 見出しは人が読むための名であり、塊が値の正本である。塊の `id` と見出しに書いた
   id は一致させる。散文は見出しと塊の周りに自由に書いてよい。
4. **JSON は塊を並べて描く。** 描き手は `render-projection.py` の新しい口とし、向きは
   .md から JSON への一方通行とする（ADR-161 決定3）。並びは文書の中の出現順とし、
   同じ入力からは同じ JSON が出る。
5. **既定の `status` は `proposed`、既定の `llm_context` は `task`、既定の点検周期は
   180 日とする。**
6. **確定の一押しは `status` で表す。** 文書の `status` が `current` であることと、その文書の
   全ての値の `review_status` が `confirmed` であることを同値とする。食い違いはリンタが
   ERROR（重大度の最も重い段）で咎める。**これが「機械が下書きを起草し、人は確定の一押し
   だけを行う」の実体である。**
7. **担保の口はリンタに置く。** 検めるのは次だけである——塊が JSON として読めること、
   実体ごとの必須欄が在ること、限られた語（`kind`・`verification_status`・`review_status`・
   `authority` など）の値が語彙の中に在ること、id が文書の中で一意であること、文書の中の
   参照（流れの `from`/`to`、シナリオの `steps`、`realized_by`、`parent`）が実在すること、
   `status` と `review_status` が決定6 のとおり揃っていること。**兄弟文書は読まない**
   （per-turn の規律。NONGOAL-001 第5項）。
8. **解析の実体は共有の部品に一度だけ置く。** リンタと描き手は同じ部品を呼ぶ（規則を二重に
   定義しない。DECIDED-001 事実1）。
9. **器の版（`schema` の文字列）は描き手が持つ定数とする。** 版の進め方（#294 の
   B1（器の正本と版の進め方））は本 ADR では決めない。

## 帰結

- 触る先は次のとおりである——`_registry.py`（型・既定の位置づけ・既定の `llm_context`・
  置き場所・必須節・点検周期）、雛形 `model.md.tmpl`、共有の解析器、`docs-linter.py`
  （新しい検査群）、`render-projection.py`（新しい口）、SPEC-001・DATA-001・ICD-001 の宣言、
  対応する TEST、起草の技能 `system-map-draft`。列挙は IMPACT-011 が持つ。
- **出所の門（SPEC-029 / `map-draft-check.py`）は当面、描いた JSON に掛け続ける。** 門を
  .md の側へ移すかは、doctrine-lens 側の読み方に影響するので issue #294 で相談してから
  決める（ADR-162 の予告のとおり）。
- ADR-161 を本 ADR と同じ波で受理する。
- 保証限界: リンタが検めるのは値の**形**である。意味の正しさ（その要素が本当に在るか、
  その流れが実際に起きるか）は検めない。出所の実在は門が、確定は人が見る。
- 保証限界: 器の版が上がったときの追随の道は決めていない（B1）。
- **節名を増やすと、その字面は体系全体で禁止同義語の照合から外れる**（ADR-135 の
  覆い）。初版の案「流れ」で試験 `test_operational_extends_seed` が落ち、実測でこれを
  確かめた。以後、節名を足すときは裸の一般語を避ける。
- 保証限界: 一つの模型が複数のリポジトリにまたがるときの扱い（#294 の B8（複数リポジトリに
  またがる模型の扱い））は、門の側の `--repo` の反復で既に閉じているが、`.md` 正本の側の
  書き方は本 ADR では決めていない。
