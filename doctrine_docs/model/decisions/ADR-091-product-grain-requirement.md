# 製品の粒度の要求を _system の棚へ置く。棚の上の要求は辺で指されない

## 背景

「この製品が何を解こうとしているのか」を置く先が無い。20 型を当てて確かめた報告があり、
こちらでも測った。

**測った結果、内容は在る。木の外にしか無い。**

| 在処 | 種別 | 何が問題か |
|---|---|---|
| `README.md` の「何を解決するか」 | **ビュー** | 正本ではない。手で保守し、刻印で参照時点を示す型である。`WATCH-001` は「README の主張3件の古びを外部レビューが指した」を既に記録している |
| `spec/doctrine.ja.md` | **EXT アンカー**（`EXT-003` が指紋で見張る） | 統治木の外。アンカーの規律は「中身は写さない」 |
| `REQ-001` | REQ | 「構造規則を単一の正本として定義する」—— **文書・機能の粒度** |

呼び手の木でも同じだった。REQ 四本はすべて機能の粒度（「一つの画面は一つの問いだけに答える」
など）で、製品として何を解くかを言う文書は無い。

**つまり製品の目的は、この体系が唯一「外を指して済ませている」ものである。** 統治の値打ちは
「正本を一つ持つ」ことなのに、その一点だけ正本が木の外に在る。

置けない理由も測った。`REQ` の置き場所は `<domain>/` に固定されており、`_system/` へ置くと
`TYPE_LOCATION_MISMATCH`（error）になる。

## 却下した選択肢

**新しい型を足す（`PURPOSE`・`MISSION` など）。** 型を一つ足すと、登録簿・リンタ・雛形・投影・
技能・受入の全面に手が入る。**払う費用に対して、置きたい内容は既に `REQ` の意味に収まる** ——
`REQ` は「存在してよい理由」を持つ型であり、その主語が文書か機能か製品かの違いに過ぎない。

**`DECIDED` に節を足す。** `DECIDED` は既に決めた事実の表であり、雛形は「入れない: 迷い、
調査、提案中」と定める。製品が何を解くかは事実の一項ではなく、要求である。役が違う。

**`README` を正本と認める。** ビューは「正本をある時点で解釈した体系外の文書」であり、刻印で
参照時点を示す型である（ADR-073）。正本にすれば刻印の意味が壊れる。しかも実際に古びた。

**何もしない（外を指したままにする）。** 呼び手は監査が error 0 / warn 0 / advisory 0 の木を
持ちながら「この製品が何を解くのか分からない」と言った。**門が全部緑でも答えられない問いが
在る**という報告である。

**ドメインの要求から製品の要求へ `depends_on` を張る（当初の案）。** 実装して**できないことが
分かった**。越境依存のガードが `REQ-000 は _system の内部です。_system の ICD 宛にして
ください` と拒み、`_system` に ICD は無い。実測でも、`_system` の正本
（`DECIDED-001`・`NONGOAL-001`・`WATCH-001`）を frontmatter の `depends_on` で指している文書は
**一件も無かった**。**横断の正本は本文で参照され、辺では指されない**のがこの体系の規約である。
当初案はその不変条件と当たるので捨てた。

## 決定

**製品の粒度の要求を `_system/` の棚へ置く。棚の上の要求は辺で指されないので、逆孤児の対象に
しない。**

1. `REQ` の置き場所に `_system/` を足す。**`_system/` は既に横断の三本
   （`DECIDED`・`NONGOAL`・`WATCH`）を置く棚である** —— 横断・一木に一つ・正本という性質が
   揃っており、製品の要求はその仲間である。棚は既に在り、`REQ` が乗れなかっただけである。
2. **粒度は置き場所が言う。** `_system/` の `REQ` は製品の粒度、`<domain>/` の `REQ` は文書・
   機能の粒度とする。新しい欄を作らない（既存の規約が既にそう読める）。
3. 雛形の要求文を「この文書・機能**または製品**が存在してよい理由」へ広げる。
4. **`_system/` の `REQ` を逆孤児の対象から外す。** 理由は上のとおり —— 棚の上の正本は辺で
   指されない。ドメインの `REQ` は引き続き対象であり、**広げただけで緩めていない**。
5. **置き場所の規則を手書きの期待表で凍らせる。** 変えたのに何も落ちなかった（`TYPES`・
   既定 `status`・既定 `llm_context` は凍結済みだったのに、置き場所だけが凍結されていなかった）。
6. **この体系自身の製品の要求を書く。** 内容は `README` の「何を解決するか」から移す（新しく
   考えるのではなく、既に在るものへ正本を与える）。**使わない仕掛けを足さない**（ADR-084 の
   規律）。常時投入には入れない —— 上限への影響を測っていないので、既定の `task` に留める。

## 帰結

- 製品の目的が木の中に正本を持つ。`README` はビューとして、その正本を解釈する立場に戻る。
- 型が増えない。20 型のまま、置き場所の規則が一行広がるだけである。
- 保証限界: **粒度は機械で判じられない。** 置き場所で表すと決めたが、`<domain>/` に製品の話を
  書くことも `_system/` に機能の話を書くこともできる。取り違えは人とレビューが見る。
- 保証限界: **`_system/` の `REQ` は逆孤児の検査から外れる。** 誰も実現していない製品の要求が
  在っても、機械は咎めない。棚の上の正本が辺で指されない規約の裏返しであり、意図した取引で
  ある。実現の対応は本文（`受入基準参照` の節）が言う。
- 保証限界: 製品の要求が一つであるべきかは決めない。いまは一つ書くが、複数置くことを禁じない。
