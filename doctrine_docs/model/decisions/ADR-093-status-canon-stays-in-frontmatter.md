# 位置づけ（`status`）の正本は平文のフロントマターに留める。台帳から導出しない

## 背景

外部レビューの RFC（設計方針の提案。実装の依頼ではない）が四層の分離を提案した。うち第三層が「追記専用の台帳 + reducer を正本の状態とし、
`status` はイベントから導出して、フロントマターは投影にする」である。これが RFC の背骨で
あり、他の提案（認識の分類・連続的な昇格・定型許可の自動化）は台帳が無くても成り立つ。

**台帳が唯一きちんと解こうとしている性質は一つである** —— `status` は自己申告であり、
`current` と書けば機械はそれを信じる。RFC の受入もそう書いている（「フロントマターの
`status`・`review_by`・`updated` だけを書き換えても昇格できない」）。

**測った。その性質は、すでに証拠で縛られている。**

監査の 36 検査のうち 11 件が「申告と実態の一致」を見ている。

| 検査 | 何を咎めるか |
|---|---|
| `adr_not_landed` | 受理した決定が、現行の文書から一度も参照されない（宣言に留まる） |
| `stale_current` | 現行と名乗るが長く動いていない |
| `review_by_overrun` | 再点検の期日を過ぎた |
| `stale_draft` | 下書きのまま置かれている |
| `reverse_orphan_req_no_spec` | 要求が仕様を持たない |
| `reverse_orphan_spec_no_test` | 仕様が受入を持たない |
| `trace_stale` | 仕様が実装を主張するが、指紋が食い違う |
| `trace_missing_impl` | 仕様が実装を主張するが、印が無い |
| `source_drift` | 出所が動いた |
| `view_stale` | ビューの刻印が古びた |
| `projection_drift` | 投影が正本とずれた |

**そして RFC 第5節の「係留」も、部分的にすでに在る。** 主張を成果物の指紋へ結ぶ仕掛けは
`実装の指紋`（内容の `sha256`）と `trace_stale` であり、実行環境への係留は試験の走りが出す
`PROVENANCE:`（python・platform・plugin の版・`core.fileMode`・commit。ADR-085）である。

## 却下した選択肢

**台帳を正本にし、`status` を導出値にする（RFC 第2節）。** 四つの理由で断る。前二つは測った。

1. **台帳は証拠を作らない。主張の置き場所を移すだけである。** `status: current` と手で
   書けるなら、`{"type": "effect", ...}` の一行も手で書ける。イベントを申告より強く
   信じられるのは、**verifier の同一性が attest されているとき**だけであり、attestation
   には信頼根が要る。標準ライブラリだけで動き通信もしない体系（確定事実7）に信頼根は無い。
   **attest 無しの台帳はフロントマターと同じ強さで、費用だけ高い。**
2. **追記器を迂回できる。** 非目標 第4項が「Hook が起動しない経路で書かれた文書は止められ
   ない」と既に認めている。2026-08-02 にそれを二度実証した —— Bash 経由で文書を編集したので
   ファイル単位のリンタを通らず、全件の門が後から捕まえた。**迂回できる台帳はフロントマター
   より悪い。** 文書と静かに食い違い、しかも見た目は権威的である。これは 2026-08-02 に
   繰り返し名指しした「在ることと効くこと」の最大版になる。
3. **影響範囲が桁で違う。** `status` をフロントマターから読む箇所は 34 箇所・8 ファイル。
   加えて呼び手の実装、203 文書すべて、確定事実3（必須キー8個）の置換が要る。
   **払う費用に対して、得るのは「申告の置き場所が変わる」ことである。**
4. **製品の要求と当たる。** `REQ-000` は「情報片の位置づけが失われることを、量ではなく構造で
   防ぐ」ことを求める。**平文を読めば位置づけが分かる**のがこの体系の値打ちであり、常時投入
   される文脈は文書そのものである。導出値にすると、reducer を走らせるまで誰にも分からない。
   **平文が正本であることが、この体系が LLM と噛み合う理由そのものである。**

**台帳を「補助の記録」として持ち、正本にはしない。** 二つ目の正本になる。reducer の答えと
フロントマターが食い違ったとき、どちらが勝つかを決められない。同じ事実を二箇所に持つ形で
あり、ADR-089 で消したばかりの形である。

**attestation を伴う不変条件を採る（`attested`・`lease_held`・`capability(scope)`）。**
単一リポジトリ・単著の体系に権限主体を発明することになる。**信頼根が無いので、
attest は名前だけになる。** 非目標 第14項が同じ判断を既に下している（検証できない申告は
誤った安心の素になる）。

**何もせず、RFC を開いたままにする。** 開いた問いは同じ提案として戻り、そのたびに同じ費用を
払って同じ結論に至る。**断ったことを、断った理由ごと記録する。**

## 決定

**`status` の正本は平文のフロントマターに留める。追記専用の台帳を持たず、`status` を
イベントから導出しない。自己申告を縛るのは、正本の置き換えではなく証拠の検査とする。**

1. **フロントマターの `status` を正本のままとする。** 確定事実3（必須キー8個）は守る。
2. **追記専用の台帳を持たない。** 正本としても補助としても持たない。
3. **attestation を要する不変条件は採らない。** 信頼根を持てないからである。
4. **自己申告への対処は証拠の検査の線で行う。** 既存の 11 検査がその線であり、足すなら
   その線に足す（新しい正本を作らない）。
5. **非目標へ記録する。** やらないことの正本に一項として書き、理由を添える。
6. **再検討の条件を書く。** attestation の信頼根が持てるようになったとき（例: 署名された
   走りの成果物を機械が検められるようになったとき）、この判断は問い直す価値がある。
   ADR-079 が「再検討の条件が満たされた」を記録した形に倣う。

## 帰結

- RFC の背骨を断ったので、第2節（台帳・reducer）と第5節の attestation は入らない。
  第1節（認識の分類）・第3節（連続的な昇格）・第4節（定型許可）は台帳に依らないので、
  別々に裁ける。
- 確定事実3 と `REQ-000` を守る。呼び手の実装にも影響が無い。
- 保証限界: **`status` は自己申告のままである。** 証拠の検査は「申告と実態の食い違い」を
  咎めるが、**食い違いが見えないように書かれた申告は通る**。RFC の受入「フロントマターだけ
  書き換えても昇格できない」は、**部分的にしか満たさない**。これを受入とは書かない。
- 保証限界: 断ったのは、いまの費用と信頼根の下での判断である。**永久の禁止ではない。**
  再検討の条件は上に書いた。
- 保証限界: 台帳を持たないので、決定の履歴は git の履歴に留まる。体系は履歴を持たない
  （非目標 第12項と同じ立場）。
