# 重複 id の採用規則を登録簿に一本化し、先勝ちに統一する

## 背景

同じ id を持つ .md が二つある状態で、どちらを採るかの規則が体系内に二つある。`inject-contract.py` の `_load_corpus` は整列パス順の最初を採る（先勝ち）。`_depgraph.py` の `_add_node` は整列パス順の最後を採る（後勝ち）。両者とも決定的で、どちらも黙ってはいない（前者は警告を、後者は `dup_ids` を記録する）が、採る文書そのものが食い違う。

この食い違いは監査の案内にも出ている。`docs-audit.py` の `shadowed_document` は「採用 <整列パス順の最後>」と直し方を示すが、注入が実際に運んだのは最初の一件である。利用者は、監査が採用したと告げた文書とは別の文書の要点を、セッション開始の契約で読むことになる。

「どれが正本か」は構造規則であり、DECIDED-001 事実1（構造規則は登録簿の中に一度だけ正本化する）の対象である。二つの規則が並立している現状は、その確定方針に反する。

## 却下した選択肢

- **重複時は両方を落とす（fail-closed）**: 注入からは DECIDED が丸ごと消えうる。契約が黙って弱くなるのは、別の文書を運ぶより害が大きい。グラフでは端が一斉に解決不能になり、越境依存の判定まで崩れる。復元力を完全性より採る方針（§1.10）にも反する。
- **後勝ちに揃える**: 後から入った衝突が、既にある文書から id を奪う。既存の文書が黙って影へ落ちるほうが、新しく来た側が影へ落ちるより害が大きい。直し方の案内（名前を変える）を向ける先も、後から来た側であるほうが自然である。

## 決定

採用規則を `_registry.resolve_duplicate_id(paths)` として登録簿の中に一度だけ定め、**先勝ち**（整列パス順の最初）に統一する。

- `_depgraph.py` の `_add_node` と `inject-contract.py` の `_load_corpus` は、この関数を呼んで採用先を決める。自前の整列規則を持たない。
- 監査の `shadowed_document` が示す採用先も、同じ関数から引く。案内と実際の採用を一致させる。
- 影に隠れた側（採用されなかった文書）は、これまでどおり error で挙げる。

## 帰結

- 「どれが正本か」の答えが体系内で一つになる。監査が告げる採用先と、注入が実際に運ぶ文書が一致する。
- 直し方が一つに定まる。衝突を起こした側（整列パス順で後ろ）が別の id を取るか `archive/` へ退く。
- 既知の限界: 重複の発生そのものは防げない。ガードが起動しない経路で作られた文書は止められず（NONGOAL 第4項）、監査の `shadowed_document` が後から error で挙げるところまでが構造の受け持ちである。
