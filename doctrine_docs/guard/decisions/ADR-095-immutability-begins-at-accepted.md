# ADR の不変は accepted から始める。proposed は下書きとして直せる

## 背景

**語彙は最初から下書きの状態を持っていた。ガードがそれを使えなくしていた。**

測った。

| 測ったこと | 結果 |
|---|---|
| `status_allowed("ADR")` | `accepted`・`deprecated`・`proposed`・`superseded` —— **`proposed` を許している** |
| SPEC-003 の carve-out | `proposed→accepted` の遷移を**明記している**（昇格の道は設計されていた） |
| `proposed` の ADR の本文編集（実測） | **deny**。「既存ADR は改変できません」 |
| 木に在る `proposed` の ADR | **0 件** |

不変ガード（Guard1）は `status` を見ていない。**存在する ADR を、存在した瞬間から凍らせていた。**
だから下書きの状態は誰にも使えず、一件も生まれなかった。

**痛みは記録されている。** ADR-044 はこう書いた —— 「Wave 群の実装中に**何度も遭遇し、
いずれも『削除して作り直す』で回避した**」。そのとき採られた決定は、**迂回路の明文化**で
あってガードを直すことではなかった。2026-08-02 から 03 にかけて、こちらでも三度払った
（一本の ADR を、用語の所見を直すために三回書き直した）。

そして報告の RFC（設計方針の提案）第3節は「全決定は candidate から始め、重要性が観測された時点で昇格する」
を求めている。**それが求める候補の状態は、語彙に既に在った。**

## 却下した選択肢

**迂回路のままにする（ADR-044 の現状）。** 「削除して作り直す」は、下書き中の推敲を毎回
全文の書き直しにする。**決定を先に書く費用を上げる** —— そして ADR-051 は「決定を含むなら
ADR を先に置く」と定めている。費用が高いほど、その規律は破られる。

**ADR の不変そのものを緩める。** `accepted` の不変は履歴の完全性であり、この体系の芯である。
**守る。** 変えるのは「いつから不変になるか」だけである。

**新しい `status` を足す（`draft` など）。** 語彙は既に `proposed` を持つ。ADR-091・ADR-092
と同じ判断 —— **棚は在って、乗れなかっただけである。**

**`proposed` を許すが、放置を咎めない。** `proposed` は現行でないので、孤児・逆孤児・
`adr_not_landed` の**どの検査からも見えない**。見えないものは忘れられる。
**下書きの墓場を作ることになる。**

**台帳で候補を持つ（RFC 第2節）。** ADR-093 で却下した。台帳は証拠を作らず、
主張の置き場所を移すだけである。

## 決定

**ADR の不変は `accepted` から始める。ディスク上の実効 `status` が `proposed` の ADR は、
本文を直せる。放置は監査が咎める。**

1. **不変ガードの凍結を `accepted` から始める。** ディスク上の実効 `status` が `proposed` の
   ADR に対しては、本文の編集を許す。判定はディスクの状態で行う（編集後の申告ではない）。
2. **逆向きは開かない。** `accepted → proposed` は carve-out の外に留める。**実測で拒まれる
   ことを確かめ、試験で凍らせる** —— 受理済みを下書きへ落として書き換える道を作らない。
3. **アーカイブの不変は変えない。** `archive/` の下と `status: archived` は、置き場所に依らず
   不変のままとする（ADR-027）。
4. **放置を咎める検査を足す。** `stale_proposed`（WARN）—— `proposed` のまま閾値を越えて
   更新が無ければ挙げる。**閾値は下書きと同じつまみを使う**（新しいつまみを配らない。
   ADR-084 の規律）。咎めるのは放置だけで、`proposed` であること自体は咎めない。
5. **既存の木で所見は増えない。** 木に `proposed` の文書は一件も無い（実測）。

## 帰結

- 決定を先に書く費用が下がる。**ADR-051 が守りやすくなる** —— 決定を含むと判じたら、
  まず `proposed` で置いて、推敲してから `accepted` へ動かせる。
- RFC 第3節（連続的な昇格）が、**台帳もイベントも reducer も無しで**部分的に入る。
  候補の状態が使えるようになるだけであり、**昇格の判定は人がする**。
- ADR-044 の迂回路は、下書きでない ADR（既に `accepted`）に誤りを見つけたときの道として
  そのまま生きている。**置換しない** —— あちらは受理済みの直し方を定めており、こちらは
  受理前の状態を使えるようにする。役が違う。
- 保証限界: **受理の判定は機械がしない。** 何を `accepted` にするかは人が決める。
  RFC が求める「重要性が観測された時点で自動昇格」は入らない。
- 保証限界: **`proposed` の ADR は現行でないので、投影にも常時投入にも出ない。**
  見張りは `stale_proposed` だけであり、それは放置の期限だけを見る（中身は見ない）。
- 保証限界: `proposed` の本文は自由に書き換わるので、その推敲の履歴は git にしか残らない
  （非目標 第12項と同じ立場）。
- 保証限界: `proposed` を許す型は 20 型すべてである。この決定が触るのは ADR の不変だけで、
  他の型の書き換えは元から自由だった。**放置の検査だけが全型に効く。**
