# この体系が解くこと（製品の粒度）

製品の粒度の要求である（ADR-091）。粒度は置き場所が言う —— `_system/` に在るものは製品の
話であり、`<domain>/` に在る `REQ` は文書・機能の話である。

常時投入には入れない（既定の `task`）。上限は 12000 トークンで（確定事実6）、常時投入へ
足すなら上限への影響を測ってから決める。**測らずに常時の側へ足さない。** 製品の目的は
変わらないものであり、入口の案内（`CLAUDE.md`）と投影から辿れる。

内容は新しく考えたものではない。`README.md` の「何を解決するか」に既に書かれていたことへ、
**木の中に正本を与えた**ものである。それまで製品の目的は、この体系が唯一「外を指して済ませて
いる」ものだった。

## 要求文

**LLM を交えた開発で、情報片の位置づけ（現行・廃止・未決・根拠）が失われることを、量ではなく
構造で防げること。**

解くべき困りごとは二つある。

1. **同じ見た目で並ぶ。** 仕様・実装・調査・判断・廃止・未決が、同じ粒度と同じ見た目で並ぶ。
   後から読むと、どれが現行で、何に依存し、なぜそこにあるかが分からない。LLM 自身も、廃止や
   古いログを現行として再採用する。
2. **量で対策すると悪化する。** 常時投入を増やすと、コーディングエージェントの成功率はむしろ
   下がり、推論の費用は増える（入力が長いほど成功率が下がるという知見）。

したがって解き方は「量を増やす」ではなく、**各情報片に位置づけ・出所・依存・現行性を付与して
追跡可能にする**ことである。

## 優先度

最上位。この要求が満たされないなら、他のすべての要求は手段として意味を持たない。

## 受入基準参照

この要求は単一の仕様では実現しない。**狭い要求（`<domain>/` の `REQ`）と、それらが指す
`SPEC`・`TEST` の全体が実現する。** 逆孤児の判定はこの階層を認める（ADR-091）。

横断の受入は次の三本が持つ。

- `DECIDED-001`（横断の確定方針）—— 何を決めたか。
- `NONGOAL-001`（横断のやらないこと）—— どこまで保証しないか。
- `WATCH-001`（横断の退行監視）—— 何を戻してはならないか。

要求の番号（`R1`〜`R12`）と発火経路の対応は `SPEC-025`（被覆マトリクス）が持つ。

## 出所

- `README.md` の「何を解決するか」（ビュー。この文書が正本になった後は、こちらを解釈する立場）
- `spec/doctrine.ja.md`（`EXT-003` が指紋で見張る上流の設計書。中身は写さない規律のため、
  ここには要点だけを置く）

## 覆わないもの

- **正しさは保証しない。** 位置づけを付けても、内容が真であることは別である
  （`NONGOAL-001` 第1項・第7項と同じ限界）。
- **量の削減そのものを目標にしない。** 少なく書くのは思想であって、この要求の受入条件では
  ない。
