# 変更フロー全文（§3.8）

更新の順序は `ADR` → 現行 `SPEC` → 実装 → テスト → LLM（大規模言語モデル）へ渡す情報 → 廃止整理。順序を守る。「何を変えたか」（`CHANGE`／git）と「なぜ決めたか」（`ADR`）を分ける。`[R3][R4]`

## 各段が生む成果物

| ステップ | 生む成果物 | 何を書くか |
|---|---|---|
| 1 捕捉 | `CHANGE`（`proposed`） | 変更内容・理由・要求元・影響の初期見積 |
| 2 前向き | （列挙） | 波及する文書・実装・テスト |
| 3 逆向き | （列挙） | 逆参照（依存元） |
| 4 影響 | `IMPACT`（`current`） | 影響する文書・実装・テスト・工数見積。感想は書かない |
| 5 境界 | （分類） | ドメイン跨ぎは相手の ICD を通す |
| 6 決定 | `ADR`（`accepted`） | 背景・却下した選択肢・決定・帰結。根拠 |
| 7 仕様 | `SPEC`（更新） | 必須4節を保つ |
| 8 契約 | `DATA`・`API`（更新） | データ契約・接点 |
| 9 実装 | `IMPL`（更新） | 影響する部品を指す |
| 10 テスト | `TEST`（更新） | 受入基準への対応・退行観点・合否基準 |
| 11 注入 | `DECIDED`・`NONGOAL`・`WATCH`・投影 | 注入する事実を更新し、投影を描き直す |
| 12 退行 | `WATCH`（更新） | 戻してはならない事項・`review_by` |
| 13 廃止 | （降格） | 一段だけ降ろす・`superseded_by`・本文は渡さない |
| 14 仕上げ | `CHANGE`（閉じる） | 「何を」は `CHANGE`／git、「なぜ」は `ADR` |

## 軽い経路（決定を含まない変更。ADR-051）

決定を含まない変更（誤字・言い回し・書式・リンクの張り替え・投影の描き直し・`updated` の更新）は、ステップ 2・3（影響の列挙）と、ステップ 7 以降の更新順序（現行 `SPEC` → 実装 → テスト → 投影）だけを通る。ステップ 1（`CHANGE`）・4（`IMPACT`）・6（`ADR`）は要らない。

| | 決定を含む | 決定を含まない |
|---|---|---|
| 1 捕捉（`CHANGE`） | 要る | 要らない（「何を変えたか」は git が持つ） |
| 2・3 影響の列挙 | 要る | 要る（安く、`[R4]` の中核） |
| 4 影響（`IMPACT`） | 要る | 要らない |
| 5 境界の分類 | 要る | 越境するときだけ |
| 6 決定（`ADR`） | 要る | 要らない |
| 7〜11 仕様・実装・テスト・注入 | 順序どおり | 順序どおり |
| 12 退行（`WATCH`） | 生まれたときだけ | 生まれない |
| 13 廃止整理 | 降格があるときだけ | 降格が起きない |
| 14 仕上げ | 要る | 要らない |

分けるのは規模ではない。既定値を一つ変える一行も、選べる案から一つを選んだのなら決定である。途中で決定を含むと分かったら、その場で全段へ戻す。

不変条件の強制は経路に依らない。削除安全ガード・ICD 依存ガード・全件監査はフックと CI の層にあり、どちらの経路を通ったかを見ていない。軽い経路が省くのは記録の段であって、強制ではない。

## 順序を省かない

決定を含む変更では、順序は必須である。`ADR` を先に決めないまま `SPEC` を変えない。廃止整理を先にしない。順序を守ると、根拠（`ADR`）と現行（`SPEC`）と履歴（`CHANGE`）が混ざらない。

ステップ 4 の `IMPACT` だけは、決定（ステップ 6 の `ADR`）より先に確定する。影響分析は決定の入力であり、決定の産物ではないためである。§3.8 の「根拠が先」は、`SPEC` 以降の更新が `ADR` の後に来ることを求める規則であり、決定材料の収集（ステップ 1〜5）はその前に済ませる。
